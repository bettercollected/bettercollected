# Internal admin service

A small separate service, started from the backend image with
`python -m backend.admin.serve`. It is not part of the public API: it has its
own application, no CORS, and shares no router or container with the backend.

## Enabling the portal

The service always starts, but the sign-in portal runs only when all of these
are set; otherwise it is the bare gate (`/healthz` and 404s) and logs one
warning naming what is missing.

1. `PLATFORM_ADMIN_EMAILS` **(required, set by you)** in the root `.env`: the
   super admin list, comma-separated. Only these addresses can sign in.
   `deploy.sh` never writes it and prints a notice while it is unset.
2. `SETTINGS_MASTER_KEY` and `BC_ADMIN_PASSWORD`: generated by `deploy.sh`
   into the root `.env` on first run, never overwritten. Back up the master
   key; it cannot be recovered. `BC_ADMIN_PASSWORD` and `BC_ADMIN_MIG_PASSWORD`
   go unencoded into database URLs, so they may use only letters, digits, `.`,
   `_`, `~` and `-`; `deploy.sh` and `postgres/ensure-admin-roles.sh` refuse
   anything else (generated values are hex).
3. Sign-in codes are mailed, so set `MAIL_SMTP_SERVER`, `MAIL_SENDER` (and
   `MAIL_USER` / `MAIL_PASSWORD` if needed) in the root `.env`. Compose reads
   them from there for this service, which has no `env_file`.

The three portal settings default to empty in the compose file instead of
being marked required: `docker compose config` and existing deployments keep
working, and an upgrade that has not set the admin list starts in the bare-gate
mode instead of failing.

## Network

- Published on the host's loopback only (`127.0.0.1:${ADMIN_PORT:-8100}`) and
  never referenced by nginx. Reach it from elsewhere with an SSH tunnel:
  `ssh -L 8100:127.0.0.1:8100 <host>`, then open `http://localhost:8100`.
- Two networks, and not `default`:
  - `admin-edge` (`ADMIN_EDGE_SUBNET`, default `172.30.77.0/29`), with only
    the admin service on it, carries the published port. Docker's port
    publishing makes host traffic arrive from that network's gateway
    (`ADMIN_EDGE_GATEWAY`), which is allowed in addition to `ADMIN_ALLOWED_IPS`.
  - `admin-db` is `internal` (no gateway, no route out) and shared only by the
    admin service and `app-postgres`. The service connects as the `bc_admin`
    role, which can use schema `admin` only.
- **What `ADMIN_ALLOWED_IPS` does and does not protect.** In this layout every
  connection from the host reaches the service as the `admin-edge` gateway
  (`ADMIN_EDGE_GATEWAY`), which is always allowed, so the service cannot tell one
  client from another. `ADMIN_ALLOWED_IPS` therefore restricts nothing that
  arrives through the published port: it only matters when clients reach the
  service with their own address (a different network layout, or real proxies
  listed in `ADMIN_TRUSTED_PROXIES` that report it in `X-Forwarded-For`). The real
  boundary is the host port binding (`127.0.0.1` only) and who can log in to the
  host: any local process, and any reverse proxy running on the host, passes the
  address gate. **Never put a proxy in front of port 8100** and never publish it
  on another interface. Consequences: session address binding, the "new address"
  notice and the address in audit rows show the gateway for everyone; the per-address
  limits cannot separate clients, so the pre-sign-in limits also use the (email)
  and (challenge) dimensions instead of one global address bucket (see "Sign-in
  and sessions"). At start the service logs a WARNING when the gateway is set and
  `ADMIN_TRUSTED_PROXIES` is empty, because that is this situation.
  If a proxy is unavoidable, set `ADMIN_TRUSTED_PROXIES`, `ADMIN_ALLOWED_IPS` and
  `ADMIN_ALLOWED_HOSTS` / `ADMIN_PUBLIC_ORIGINS` for it; `deploy.sh` prints a reminder when
  any of those is set in the root `.env`. An SSH tunnel is the supported way in.
- **Cookies and ports.** The `__Host-` cookies carry no port, so a browser sends
  `__Host-bcadmin` to every service on the same host name, whatever the port
  (`localhost:3000`, another tunnel, a second environment's portal tunnelled to
  another port). `SameSite=Strict` does not help (same site), though `Origin` and
  `Sec-Fetch-Site` are still checked. Use a host name of your own that resolves to
  loopback for each environment (for example `admin.localhost` in the `/etc/hosts`
  of the machine that opens the tunnel, added to `ADMIN_ALLOWED_HOSTS` and
  `ADMIN_PUBLIC_ORIGINS`), which gives each portal its own cookie jar, and do not
  run untrusted software on a machine that holds a tunnel.
- Because the service is not on `default`, no other container can resolve or
  route to it. Attaching it to `default` as well would let Docker pick which
  network host traffic comes from; keep the layout as it is.
- Compose 2.24 with Docker Engine 27 sometimes attached a container on two
  networks (`app-postgres`, `admin`) to only one of them when the networks were
  created in parallel (3 to 5 of 10 up/down runs). The compose file therefore
  gives those services explicit network `priority` values; with them, 0 of 40
  plain `docker compose up` runs lost a network. Setting
  `COMPOSE_PARALLEL_LIMIT=1` in the root `.env` does not help in this Compose
  version (5 of 10 runs still lost a network), so it is not relied on;
  `deploy.sh` and the check script still export it as an extra precaution (this
  also serialises `pull` and `up --build`, so deploys can be slower). A
  service that logs a name-resolution failure for `app-postgres` has hit this:
  `docker compose up -d --force-recreate app-postgres admin`.
- `scripts/admin-compose-check.sh` verifies all of this with real containers
  (see below).

## Acceptance check

`scripts/admin-compose-check.sh` needs docker (Compose 2.24.4 or newer), curl and openssl. It
builds the backend image from the checkout unless `ADMIN_CHECK_IMAGE` names
one, then starts its own throw-away compose project on a random free loopback
port and an unused subnet, with new secrets, and removes everything on exit
(`KEEP=1` leaves it up). It checks, against the running containers: the
host reaches `/healthz` and the sign-in page through the real gateway address;
the LAN address is refused; a container on the default network cannot reach
the service; the health check is healthy in bare-gate mode and with a database,
master key and admin list; `docker compose config` parses with and without the
optional variables, and on a fresh checkout without `.env.deployment` or the
per-service env files (the services that read `.env.deployment` get a copy of
`.env.deployment.example`, never your own file); the container is read-only,
non-root and capability-free;
and `bc_admin` can read only its own schema and cannot update the audit log. It
also checks the deployment around the service: a `.env` holding only what
`deploy.sh` generates plus the operator's values renders; only the intended
services publish a port (Temporal and the databases publish none); the master
key reaches the store readers, the admin service and the task runner and never
the Temporal worker; DEBUG and API_DOCS_ENABLED are not pinned; the Temporal and
Umami databases take the generated password; and the host commands work through
compose (`bootstrap-keys` prints no key material and is refused the second time,
the import dry run and the drift check read the compose configuration from
standard input, and the one-off container has none of the stack's keys in its
environment). It also renders the compose file next to a `.env.deployment` filled
with dummy Stripe, Google, mail, Mongo and key values and asserts that none reaches
a service outside the four store readers (and that the worker's whole environment is
its handful of variables), checks with real containers that the Mongo seed leaves no
`seeduser`, and that the nginx rules for Umami pass only the tracker.

## Release acceptance

`scripts/v4-compose-check.sh` is the end-to-end check to run before a release
(it complements the component check above, which stops at the admin service's
own wiring). It runs the real `./deploy.sh` in a throw-away copy of the
deployment files (`deploy.sh`, the compose files, `postgres/`, `deploy/`,
`nginx-deployment.conf`), against images built from the checkout, and removes
everything when it exits. Each stack gets its own compose project name (the
copy's directory name, as for a real install), host ports from 8100 up that are
free (all on `127.0.0.1`) and an unused subnet for the admin edge network; it
never uses the default project name or a fixed host port, so a stack running on
the same machine is left alone. Mail goes to a local mail sink (mailpit).

| Part | Flag | What it runs and asserts |
|---|---|---|
| 1 fresh | `--fresh` | `deploy.sh` on a terminal with empty volumes: every service healthy (the admin service, task runner, jobs worker and document sandbox included), every schema at its head, `bootstrap-keys` before the first service starts, the fingerprint notice and the setup token printed once, no secret value in the output, the process list, `docker inspect`/`docker top` or any container log, the webapp and the Temporal worker without secrets, no internal port published, Umami's built-in login refused, the public Umami port passing only the tracker. A second `deploy.sh` changes nothing and shows nothing again. Then the portal as a scripted browser: a wrong token and a wrong address look the same, the right token starts the setup session, an authenticator is enrolled (codes from an RFC 6238 helper), the mail test goes to the sink and the settings are saved only with its code, the wizard is finished and is a bare 404 afterwards, sign-in with the mailed code and the authenticator, the pages (`/health` with every service reporting, `/config`, `/audit`, `/settings`, `/tasks`) answer, and a read-only task is run through the portal and executed by the task runner |
| 2 upgrade | `--upgrade` | the previous release's files and published images (`v3.4.0`, `V4_CHECK_OLD_TAG`) started with their own `deploy.sh`, seeded with fake workspaces, forms, encrypted responses and users, then taken over by the new `deploy.sh`: the import path (no bootstrap), conflicts reported and never chosen, `settings-drift` clean, documents intact, the stored keyset and keys equal to the old ones, `bootstrap-keys` refused (`stack_has_data`), a `settings-prune` dry run that changes nothing, and `responses.check_undecryptable` through the portal finding no undecryptable value |
| 3 rollback | `--rollback` (runs on the stack of part 2) | `SETTINGS_STORE=off` and a redeploy: the stack serves from the files, data and store untouched; the store back on; then the previous release's files and images over the upgraded stack, and forward again |
| 4 negatives | `--negatives` | the portal is not reachable from a sibling container (by name, through the host, by its edge address) or with a foreign `Host`; the admin port is on `127.0.0.1` only; the master key is held by the four store readers, the admin service and the task runner and by nothing else (rendered and `docker inspect`); a minimal `.env` renders and four variables alone are refused |

With no flag all four parts run, about 12 minutes with the images in place (the
first run adds the image pulls and builds); `--parts 1,4` and the other flags pick
parts, and `--rollback` runs on the upgraded stack of part 2. `--keep` leaves the
stacks up for inspection. Needs docker with compose v2, `script` (the setup token
is shown on a terminal only), `uv` (it runs the portal client,
`scripts/v4_check_client.py`, which uses the standard library only), curl and
openssl; a part does not start when less than `V4_CHECK_MIN_FREE_MB` (default 2500)
of disk is free.

Images: the backend (which is also the admin service, task runner, jobs worker and
document sandbox), auth and the Temporal worker are built from the checkout as
`bc-v4check-*:local`; they and the images the run pulled are removed afterwards
(`V4_CHECK_KEEP_IMAGES=1` keeps them) and `V4_CHECK_REUSE_IMAGES=1` reuses images
with those tags. `V4_CHECK_WEBAPP=nightly|build|<image>` picks the webapp
(default: the published `nightly`, because a webapp build takes long, so the webapp
is not tested from the checkout by default). `V4_CHECK_GOOGLE=1` builds the Google
integration and deploys it too (`./deploy.sh googleform`). `V4_CHECK_OLD_TAG` and
`V4_CHECK_OLD_WEBAPP` choose the previous release for part 2 (default `v3.4.0` and
its published images). Only the `image:` lines and the host side of the published
ports differ from the files that ship. For part 2 the previous release's own
`deploy.sh` starts the old stack (with a one-line `docker-compose` shim when the host
has only the plugin), the keys of its shipped `.env.deployment`, which the new
`deploy.sh` refuses by design, are replaced by generated ones as an operator would
have done, and the dummy data is written by that release's own models and encryption.

Not covered: Polis single sign-on, TLS and DNS in front of the stack, mail through a
real SMTP server.

## Gate

Every request must pass, in order: the `Host` allowlist, then the client
address allowlist. A request that fails either gets a bare 404 and a rate
limited warning log line. Routes are registered with a required level;
anything unregistered is a 404. `/healthz` answers `ok` to loopback peers and, for host-side monitoring, the admin network gateway.
Responses carry a strict CSP and related security headers, a `Permissions-Policy`
that turns every powerful browser feature off, and, when the request arrived over
TLS (the ASGI scheme, or `X-Forwarded-Proto: https` from a trusted proxy only),
`Strict-Transport-Security` (one year, subdomains). Bodies are capped
at 64 KB and only form or JSON content types are accepted.

## Sign-in and sessions

Sign-in is by an 8-digit code mailed to an address listed in
`PLATFORM_ADMIN_EMAILS` (read once at start). The sign-in form
answers every address the same way, so it does not reveal who is an
admin. A code lasts 10 minutes, works once and allows five attempts; asking
for a new one cancels the old one. Many wrong codes across the service pause
sign-in for 10 minutes; admins are mailed once when that happens. The
sign-in mail uses the platform's `MAIL_*` settings.

Who can be locked out by what. Anyone who can reach the sign-in page can ask for
a code for a listed address and type wrong ones, so wrong **email codes** never
lock the address itself:

- they count against the pair (email, client address): five wrong codes lock that
  pair for 15 minutes, then 1 hour, then 4 hours, and the genuine admin can still
  sign in from another address with a valid code. Behind the shared gateway address
  (see "Network") the pair is everyone, so there no pair lock is applied and only
  the per-challenge limit (five attempts, then the challenge is burned) and the
  request limits below hold;
- a ceiling of 30 wrong email codes per address and hour, from any addresses, is
  an alert (an audit row `signin.failure_surge` and one mail to every admin), never
  a lock;
- code requests are limited per (email, address) (3 per 10 minutes), per address
  (10 per 10 minutes; one high flood cap for the shared gateway address) and, at a
  higher ceiling, per email (12 per 10 minutes), so one client cannot use up the
  admin's requests from another;
- the lockout mail goes out at most once per address and hour;
- the **second factor** keeps its own lock per admin email (five wrong codes in five
  minutes, escalating as above): it is reached only with a valid email code, so
  only someone who already passed the first step can feed it. Operator `unlock`
  clears that lock and the factor counters; a pair lock lapses by itself.

What brute force costs: with the limits above one address gets at most 15
guesses per 10 minutes at an 8-digit code, so a guessing run is not practical, and
a flood of wrong posts against one challenge cookie costs memory only: after a few
posts (the five counted attempts and a little slack) the service answers from memory
with no database work and no audit row, and a refused challenge writes one audit row
in total. The residual: an attacker at the same shared address as the admin can
keep requesting codes (each new request cancels the previous code), which is a
nuisance, not a bypass; the host boundary is what keeps them out.

A session cookie (`__Host-bcadmin`, `Secure`, `HttpOnly`, `SameSite=Strict`) holds
a random token; only its hash is stored. Sessions end after 30 minutes idle or
8 hours in total (`ADMIN_SESSION_IDLE_MINUTES`, `ADMIN_SESSION_ABSOLUTE_HOURS`
can only shorten these), are bound to the client address and browser, and at
most three stay live per admin. A signed-in session whose second factor is still
pending can reach only `/mfa/enrol*` (no factor yet), `/mfa/verify` (factor set up)
and `/logout`. Removing an address from
`PLATFORM_ADMIN_EMAILS` ends its sessions at the next start or request.
Every state-changing request needs a CSRF token and a same-origin
`Origin` (`ADMIN_PUBLIC_ORIGINS`). The session's token is derived from its id
and its current token hash, so it changes whenever the session token rotates.
The sign-in forms, shown before a session exists, use a signed double-submit
cookie; cookies do not separate ports on `localhost`, so another local service
could plant that cookie, and what actually protects those forms is the `Origin`
(scheme, host and port) and `Sec-Fetch-Site` check, which every state-changing
request must pass. Operator commands:
`python -m backend.admin unlock <email>`, `resume-sign-in`, `revoke-sessions [email]`.

## Second factor, recovery codes and step-up

Every admin needs an authenticator app (TOTP, 6 digits, 30 s). The first
sign-in leads to `/mfa/enrol`: scan the QR code (drawn by the service, nothing
is fetched) or type the key, confirm with one code, and ten single-use recovery
codes are shown once. The secret is stored encrypted, bound to its row and the
address. A code works once (a replayed or concurrent duplicate is refused), one
step of clock drift either way is tolerated, and five wrong codes in five
minutes (or fifteen in a day) lock the address with the same escalation as above.
Guesses are reserved before a code is checked, so at most five are evaluated per
five minutes however many requests arrive at once.
A recovery code can be used instead of an authenticator code; every admin is
mailed when one is used, when an address is locked, when a factor is set up,
and when an admin signs in from an address not seen in their recent sessions.

Sensitive actions that keep an account recoverable (making new recovery codes,
adding or replacing the authenticator) need a fresh code **sent with that
request**: the 300 seconds that sign-in itself opens do not count, so a stolen
session cookie alone cannot do them. Making new recovery codes also mails every
admin. Ending another admin's session needs a fresh code within
`ADMIN_STEPUP_SECONDS` (default 300, at most 600); the portal asks for it on a
prompt page. Actions that
must not ride on that window use a single-use token (120 s) bound to the exact
action, from `POST /api/stepup`.

If the authenticator and the recovery codes are both lost, only the operator on
the host can reset the factor (there is no reset by another admin, and none by
email). The reset is audited, revokes the admin's sessions, mails every admin and
makes the next sign-in enrol again:
`python -m backend.admin reset-factor --email <address> --yes`. On a
single-admin installation this command is the only way back in.

Without `ADMIN_DATABASE_URL`, `SETTINGS_MASTER_KEY` and `PLATFORM_ADMIN_EMAILS`
the service starts as the bare gate: `/healthz` and 404s only, with one warning
naming the missing settings (never their values); see "Enabling the portal"
above for how the compose service receives them. Settings that are present
but invalid stop startup.

## Portal pages (viewing)

After the second factor the portal shows a shell (navigation, the signed-in
address, sign out, a notice area) and these pages. Every one is a `GET` at the
`SECOND_FACTOR` level; none changes state. The pages that do change state are
described under "Settings pages" and "Task pages" below.

| Page | What it shows |
|---|---|
| `/` | Cards linking to the pages below |
| `/health` | Service heartbeats from `settings.service_state` (names and numbers; no report for 120 s is "stopped"), database reachability, the Alembic state of the `admin`, `app`, `auth` and `google` schemas (current against the head the deployed code expects), and the mirror outbox (`mirror_write_failures`) of the backend, auth and Google services: unresolved and total rows in PostgreSQL, red while any is unresolved. The other schemas are read through definer functions (see below); MongoDB outboxes are not shown, the admin service has no MongoDB access |
| `/config` | The settings registry joined with the store and the env-override names services report: section, readers, type, reload class, tier, source (store, environment, default), version, last change. Secrets show only "set" or "not set" and the last change, never a value, length, prefix or hash (the query never selects them). `NEXT_PUBLIC_*` keys are "build argument", tier T5 keys "environment only" with no values. Filters `section` and `tier` are validated allowlists (400 otherwise). Also lists the super admins from `PLATFORM_ADMIN_EMAILS` |
| `/metrics` | Platform counts (organisations, users, forms, responses, 12 weekly buckets). Counts only, read from Postgres through `admin.platform_counts_app()` and `admin.platform_counts_auth()` |
| `/audit`, `GET /api/audit` | Newest first, keyset pagination (`before` is a `seq`), filters `actor`, `action` (exact or dot-separated prefix), `outcome`, `from`, `to` (a date or an ISO time; `to` as a date includes that day), `limit` up to 200; all validated (400 otherwise). Payloads are shown masked and escaped. The page shows the chain head and points to `python -m backend.admin audit-verify`; the chain is not verified inside a request. No export |
| `/sessions` | Your live sessions (created, last seen, address, a short fingerprint of the browser identification) with the current one marked; revoke forms post, with the CSRF token, to the existing account routes |

A notice area at the top of every page carries a permanent reminder to back up
`SETTINGS_MASTER_KEY` (it cannot be recovered) and, when a service reports a
pending restart, a restart notice.

The counts come from two functions, `admin.platform_counts_app()` and
`admin.platform_counts_auth()`, created by `postgres/ensure-admin-roles.sh`, not by
an Alembic revision: the admin roles cannot read the `app` and `auth` schemas and
the migration role owns nothing there. Each is a SECURITY DEFINER owned by a
dedicated role of its own schema, `bc_count_app` and `bc_count_auth` (NOLOGIN, no
superuser, no create rights anywhere, owning only its function). A role has `USAGE`
on one schema and column-level `SELECT` on only the columns its function reads, so
it holds nothing the schema's own owner role (`bc_app`, `bc_auth`) does not already
hold. **No definer function reads tables of more than one owning role.** That is
the point: a table owner can replace its table with a view that calls its own
function, and that function then runs as whoever reads the view. Here the reader is
a role with the owner's own rights and nothing more, so planted code gets nothing
from another schema, from `admin` or from `settings`
(`tests/admin/test_db_privilege_model.py` plants exactly that for each schema). The
functions take no arguments, write nothing, pin `search_path` and are executable by
`bc_admin` alone; the script re-applies the grants on every deploy, so they appear
once the application migrations have created the tables. The admin service adds
the two answers up in Python (`repositories/views.py`, `combine_counts`) and treats
them as data: only whole numbers in known fields survive. The counts follow the
Postgres store, so they are complete once the application serves from Postgres;
before the application migrations have run the page says they are not available.
(The earlier single `admin.platform_counts()` and its owner `bc_admin_counts` are
dropped by the script.)

The Health page reads the other schemas the same way. Per owning schema,
`admin.schema_revision_<schema>()` returns the revision(s) in its `alembic_version`
and `admin.outbox_counts_<schema>()` the unresolved and total rows of its
`mirror_write_failures` (counts only), for `app`, `auth` and `google`. Each is owned
by that schema's count role (`bc_count_app`, `bc_count_auth`, `bc_count_google`),
which gets column-level `SELECT` on `alembic_version.version_num` and
`mirror_write_failures.resolved_at` only; EXECUTE for `bc_admin` alone, which still
has no `USAGE` on those schemas. They answer NULL until the schema's migrations have
created the table, and the page shows "missing" or "no outbox table yet". They are
not part of any service's migration chain on purpose: a function owned by the
schema's owner role, or living in its schema, could be redefined by that owner (made
`SECURITY INVOKER`, or dropped and recreated), and the portal's role would then run
the owner's code with its own rights. A release that adds such a function needs
`postgres/ensure-admin-roles.sh` run once after the upgrade (`deploy.sh` does); until
then the page says "not available" and names the script. The heads the deployed code
expects come from the revision files in the backend image: its own and, copied in by
`backend/Dockerfile`, the auth service's and the Google integration's, parsed and never
imported (`backend/admin/schema_heads.py`). The page reads the outboxes in PostgreSQL
only; for MongoDB run `python -m backend.migrate status` (and `auth.migrate`,
`googleform.migrate`) in the service's container.

## Settings pages (changing settings)

`/settings` lists every setting (filter by section or tier); `/settings/<key>`
shows one with a typed form, `/settings/<key>/history` its versions,
`/settings/integrity` runs the store verification on demand and
`/settings/notifications` lists the queued admin notices (read-only; the
sender is separate). All use the `SettingsService`, so validation, tiers,
versions, history, audit rows and notices are the service's.

Changing a setting takes two steps because the pages use no script:

1. The edit, clear, restore or purge form includes a fresh authenticator or
   recovery code and posts to `/settings/<key>/prepare`. That is the only
   mutating settings route without a token; it writes nothing. It validates the
   value, checks the typed confirmation (tier T3), checks the code, and answers
   with an "apply" page holding a single-use token.
2. The apply page posts to `/settings/<key>/set`, `/clear`, `/restore` or
   `/purge-history`. Those routes require a token issued for exactly that
   action, key, new value and the version the admin saw (the service's keyed
   action hash), so a token cannot be replayed or moved to another change. A
   change made by someone else in between is refused as stale.

A new value is carried between the steps only as an AES-256-GCM blob bound to
the session, action, key and version, valid for two minutes, so a secret never
appears in HTML, a URL, a log line or an audit row. Secrets are written
through a write-only password field and never prefilled; history shows only
"set" or "cleared" for them (the last five sealed versions are kept; "purge"
deletes the older ones). Key material (T4) shows no form, since a maintenance
task rotates it, and environment-only keys (T5) can only be read. The portal
asks for the code on every change, including tier T1 (the service itself only
requires it from T2).

Redirect messages use a fixed list of codes (`?notice=...`), never values.
`/settings/integrity/run` needs no step-up (it reads only), is limited to three
runs a minute and shows setting names with reason codes; a failed last run
adds a notice to every page.

## Settings store: what the database guards do and do not do

Schema `settings` holds signed (and, for secrets, encrypted) rows, a signed
manifest and per-service views. The triggers on its tables stop mistakes and a
compromised runtime role (no deleting entries, versions and the manifest
revision only go up by one, no future history rows, and no history row is ever
changed: a master-key rotation appends a re-wrapped copy to `settings.history_wraps`
instead of overwriting, and the database accepts a copy only when it keeps the
sealed value of the original, so a stolen portal credential cannot destroy the
backup safety net). The keyset row (`MASTER_ENCRYPTION_KEYSET`) moves to a new
version through the task runner's function only. They do not stop the
migration role, which can disable triggers. What the database cannot do is verify
a signature (the keys are not in it): a role without the master key can still
damage a row it may update (for instance re-key a data key), but it cannot produce
a row that verifies, and every such change is found by the integrity loop
(`bad_signature`, `history_unreadable`) and refused by every reader. Tampering is detected instead:
every row carries a signature, the manifest signs the full set of keys, versions
and readers, and every change is in the audit trail; `settings-verify` checks
all three against each other, including a wiped or rolled-back store.

Each reader's manifest view lists every key, version and reader set, not only
the rows that service may read: a service needs that to notice a row withheld
from it. Key names are therefore visible to every reading service; values never
are.

A change to a step-up setting must carry the setting's current version in the
step-up (`SettingsService.action_hash(action, key, value, expected_version)`).
The portal reads the version when it renders the form, binds it into the hash it
asks the step-up module to issue a token for, and passes the same
`expected_version` to the service, which checks it inside the write transaction.
A replayed token, or a form left open while someone else changed the setting,
fails with `stale_version`.

### Key material is checked when it is written

The registry names a format for the keys that are key material, and every write
(`settings-set`, `settings-import`, `bootstrap-keys`, the portal) refuses a value
that does not meet it, with a refusal code and a sentence that never shows the value:

| Key | Format | Refusal codes |
|---|---|---|
| `AUTH_JWT_SECRET`, `AUTH_INTERNAL_NOTIFY_KEY`, `TEMPORAL_API_KEY` | at least 32 characters, not a known placeholder, not a repeating or low-entropy pattern (`openssl rand -hex 32` is what the deploy scripts make) | `too_short`, `low_entropy`, `weak_secret` |
| `AUTH_AES_HEX_KEY` | a Fernet key (32 bytes, url-safe base64) of bytes that are not all alike | `weak_secret` (not Fernet), `low_entropy` |
| `MASTER_ENCRYPTION_KEYSET` | a Tink keyset Tink can build an AEAD from: key ids once each, an enabled primary key | `bad_keyset` |
| `CUSTOM_DOMAIN_ASSERTION_KEYS` | `id:secret` pairs, secrets of 16+ characters | `bad_pairs` |
| `CUSTOM_DOMAIN_WEBHOOK_SECRETS` | one or two secrets of 16+ characters | `bad_list` |

Published values are refused as before (`weak_secret`). The master key
(`SETTINGS_MASTER_KEY`) must also decode to 32+ bytes that are not nearly identical.
An upgrade imports what the old `.env` holds: a legacy short or low-entropy
`AUTH_JWT_SECRET` is now **refused with `too_short` or `low_entropy`** instead of being
moved into the hardened store; replace it (everyone is signed out once) and import
again. The services that only read the store do not apply these checks, so a value
stored earlier never stops one from starting. The keyset a stack published long ago
is still accepted (its responses could not be read with another), with the existing
warning.

### Rollback and wipe protection

The signed rows and manifest cannot be forged without the master key, but an older
validly signed state can be put back, and a database can be replaced by an empty one.
What stops that, and what does not:

- Each service keeps the highest manifest revision and row versions it accepted in
  its signed snapshot (`SETTINGS_SNAPSHOT_DIR`, a volume in the compose file). With
  `SETTINGS_STORE=required` a service **refuses to start** on a store whose revision
  is below that floor (`StoreError`: "settings store is behind this service's
  record"), and on a never-written store (revision 0) while its environment lacks a
  key it cannot run without (`AUTH_JWT_SECRET`, `AUTH_AES_HEX_KEY`): a wiped database
  looks like that. After a restore or replacement you meant to do, remove the snapshot
  directory (or the volume) and restart.
- The floor is the highest revision the service reports in `report_state`
  (`revision_applied`), and the **admin integrity check** compares it with the store:
  a manifest revision below what a live service (reported within the hour) accepted is
  `store_behind_services` on the health page and in the integrity mail, whatever the
  database's own audit trail says (a full restore brings back an older audit trail
  too, but not the running services' memory). `settings-verify` also reports
  `manifest_rollback` against the audit trail.
- Not covered: a validly signed older state on a service that starts with **no**
  snapshot (a recreated container with its volume gone, `docker compose down -v`,
  a first start) is accepted. Nothing outside the container and the database holds
  a floor for it, and an attacker who can write the database (or restore a backup)
  and also replace the service's volume could use that. The integrity check above
  is the compensating alarm; for the strongest guarantee keep the snapshot volumes
  and back them up with the master key. A wiped store on a stack that still keeps
  its secrets in the environment (not yet migrated) is indistinguishable from an
  unmigrated one, so non-secret settings (trusted proxies, SSO, webhook URLs) fall
  back to their code defaults there until the floor exists.

### The actions executor and key material

`temporal/actions-executor` runs form-creator code with `exec`, a stripped globals
dictionary and `__builtins__` set to `None`. That is not a sandbox: a known
introspection chain reaches `os.environ` from such code. The registry therefore
lists the executor as a reader of **no** key material, and its environment must hold
as little as possible: not `SETTINGS_MASTER_KEY`, not `DATABASE_URL`s of other
services, and, in time, neither `AES_HEX_KEY` nor `API_KEY` (today the executor's own
code still reads them, to decrypt action secrets and to call the backend's job
routes, so an executor that is given them exposes them to action authors; moving
decryption and the callback behind a per-run credential from the backend is the open
change). The repository's compose files do not run the executor (the deployment
workflow deploys it separately), so its environment is whatever that stack passes:
check it against `temporal/actions-executor/.env.example`.

## Host commands for the settings store

`python -m backend.admin <command>` runs on the host (in a one-off container that
has `ADMIN_DATABASE_URL` and `SETTINGS_MASTER_KEY`). The operator holds the master
key and the database role, so these commands need no second factor; every change
is an audit row with actor kind `cli`, written in the same transaction. The
commands print counts, setting names and short reason codes, never a value.

| Command | What it does |
|---|---|
| `bootstrap-keys [--export-worker FILE] [--existing-stack] [--fill-missing]` | Fresh install: generates `AUTH_JWT_SECRET`, `AUTH_AES_HEX_KEY`, `AUTH_INTERNAL_NOTIFY_KEY`, `TEMPORAL_API_KEY` and the response keyset straight into the store, prints only the keyset's key-id fingerprint (the value services report as their keyset fingerprint) and the master-key fingerprint. Refused whatever the flags when the stack holds data (users or responses in `admin.platform_counts_app()` and `admin.platform_counts_auth()`, or, only when `MONGO_URI` is in the command's own environment, a non-empty `users` or `form_responses` collection in that Mongo server; `deploy.sh`'s one-off container has no Mongo credentials, so `deploy.sh` decides the Mongo half itself, see below) or when that cannot be established (fail closed): a new keyset could not read what the old one encrypted, so an existing stack imports its keys with `settings-import` instead. Also refused when `--existing-stack` is passed, when the environment already carries one of the keys (import instead), or when the store holds one (`--fill-missing` finishes an interrupted run and adds only the missing ones). `--export-worker FILE` writes `API_KEY` and `AES_HEX_KEY`, the two copies the Temporal worker keeps (it never gets the master key), to a new private file or appends them to a private env file that has neither; `--export-worker-only` skips generation. |
| `settings-import --from-compose-config [--dry-run] [--prefer SERVICE]` | Reads `docker compose config --format json` on standard input (never written to disk) and imports each setting once, from the services that read it (`backend`, `jobs-worker`, `auth`, `integrations-googleform`, `admin`). | `setup-token [--new]` | Prints a one-time first-run setup token on the console only (refused when standard output is not a terminal unless `--allow-non-tty`). 160 bits, valid 60 minutes, one use; only a keyed hash is stored (the token is in no log and no audit row). **Admin sign-in mail.** The code that signs an admin in arrives by mail, so a
mail setting that cannot deliver locks every admin out. The `admin_mail` section
(`ADMIN_MAIL_USER`, `_PASSWORD`, `_SMTP_SERVER`, `_SMTP_PORT`, `_SENDER`,
`_STARTTLS`, `_SSL_TLS`, `_USE_CREDENTIALS`, `_VALIDATE_CERTS`; tier T3, read by
the admin service only, never the public `mail` section) therefore cannot be
saved by `SettingsService.set` or `import_once` unless the caller passes
`mail_verified=True`, its statement that a test mail was delivered with exactly
these settings. `settings-mail-apply` does that after the code round trip;
`settings-set` and `settings-import` cannot. Clearing and restoring an earlier
(already tested) version stay possible. An environment value still wins over the
store, which keeps `ADMIN_MAIL_*` in `.env` as the break-glass. The portal reading
these keys, and its own test-and-confirm flow, are the setup wizard below.

The setup token lives in `admin.setup_tokens` (migration `0011_setup_tokens`: one
active token at a time, 20 wrong tries lock it). `services/setup_token.py` has the
primitives the wizard uses (`issue`, `redeem`, `active`).

## First-run setup wizard

A fresh install has no way to sign in yet (codes are mailed, mail is not set up).
The wizard closes that gap without opening a door: it exists only while no admin
has a confirmed second factor **and** a valid setup token waits. Its pages sit
behind the same Host and address gate as everything else, and every refusal is the
bare 404 of an unknown path.

1. On the host, print a token (once, on the console; it is in no log):
   `python -m backend.admin setup-token` (`--new` replaces an unused one). It is
   160 random bits, valid 60 minutes, usable once.
2. Open `/setup` (through the SSH tunnel) and enter the token and one address from
   `PLATFORM_ADMIN_EMAILS`. The token travels in the POST body only, never in a URL.
   Wrong tries count against the token only within limits (5 per client and 15
   minutes, 8 per address and hour); past them a wrong try is refused without being
   counted or audited and the right token still works, so a flood from the one
   address everything shares cannot burn the token. 20 counted wrong tries lock the
   token for good (every admin is mailed, if mail works); `setup-token --new`
   replaces a locked or lost one. A wrong token, an unlisted address, an
   expired or locked token, a finished setup and a rate limit all get the same
   answer (a redirect back to `/setup`, which is the bare 404 when setup is closed)
   and the same database work. A right token creates a
   `setup` session: 60 minutes, 15 idle, bound to address and browser, able to
   reach second-factor enrolment and sign-out only. Every admin is told it started.
3. Enrol an authenticator on the portal's own enrolment pages and save the ten
   recovery codes. The first confirmed factor ends the token's life: `/setup`
   disappears and `setup-token` refuses (`reset-factor` is the only way back). The
   session becomes a normal signed-in one.
4. **Mail** (optional, `/setup/mail`): enter the server settings. A test mail with a
   six-digit code goes to your own address using exactly those settings; the
   `admin_mail` keys are saved (through the settings store, audited, with the
   delivered-test guard) only after you type the code. Saving needs a fresh
   authenticator code. Defaults are STARTTLS on port 587; STARTTLS and TLS from the
   start are never both on (refused by the server too), and implicit TLS needs its
   port stated. A saved password is never sent to a different server, and never over weaker
   transport than it was saved with: if the server, port or user name changed, or
   STARTTLS / TLS / certificate checking changed to something other than "protected
   and verified" (or to something different from an insecure setting it was already
   saved with), the password must be typed again. The environment (`ADMIN_MAIL_*`, then `MAIL_*`) wins over
   saved settings; the service reloads saved ones at most once a minute. You can
   skip the step and run `settings-mail-apply` on the host later.
5. **Finish** (`/setup/finish`): the master key fingerprint and a backup reminder
   (there is no escrow: nothing here stores the key). Tick the box and the wizard
   is closed in the database for good and every admin is mailed.

Steps 4 and 5 are reachable only by the admin who used the token, until they finish
or two hours after the token was used. After that every `/setup` path answers 404.
They are not reachable "before any factor exists": the second factor comes first, so
that nothing is saved without one.

Every step is audited (`setup.token_redeemed`, `setup.token_refused`,
`setup.token_locked`, `setup.mail_test`, `setup.mail_saved`, `setup.mail_skipped`,
`setup.completed`, plus the session, factor and settings rows of the existing
machinery); none holds a token, a code or a password. State lives in
`admin.setup_state` (migration `0012_setup_state`, which also allows the `setup`
session state). A lost token: `setup-token --new` before the first enrolment. The
wizard adds no write path of its own to the settings store.

## Deploying with `deploy.sh`

What you provide, and what `deploy.sh` generates (once; a value already present is never changed):

| | Where | Who |
|---|---|---|
| `PLATFORM_ADMIN_EMAILS` | root `.env` | you (required to enable the portal) |
| `ADMIN_ALLOWED_IPS` | root `.env` | you, only when you reach the portal from another address than the host (default `127.0.0.1/32`) |
| `SETTINGS_MASTER_KEY` | root `.env` | generated; **you back it up** (its fingerprint is printed at the end of a new install) |
| `DATABASE_URL` | not set in the bundled stack | compose builds each service's URL with its own database role; pointing the stack at an external Postgres is not covered by this compose file |
| database role passwords, `UMAMI_APP_SECRET`, `BC_TEMPORAL_DB_PASSWORD`, `BC_UMAMI_DB_PASSWORD` | root `.env` | generated (the last two for new volumes only). `BC_MONGO_ROOT_PASSWORD` is no longer generated: a 4.1 stack has no MongoDB, and a 4.0 stack keeps the one it has for the import |
| `API_KEY`, `AES_HEX_KEY` | root `.env` | generated into the store, copied here for the Temporal worker only |
| `AUTH_JWT_SECRET`, `AUTH_AES_HEX_KEY`, `AUTH_INTERNAL_NOTIFY_KEY`, `TEMPORAL_API_KEY`, `MASTER_ENCRYPTION_KEYSET` | the settings store | generated by `bootstrap-keys` (nothing printed); imported on an upgrade |

So a bundled install needs one value from you, `PLATFORM_ADMIN_EMAILS`, plus `ADMIN_ALLOWED_IPS` in the cases above; the master key is the one value you keep safe.

**New install.** `deploy.sh` generates the secrets above, starts the database, creates the roles and applies every migration (including the `settings` schema), then runs `bootstrap-keys` in a one-off container before any service starts: the keys go into the store as the `cli` actor, only the fingerprint is printed, and the two worker copies are written to `.env` (mode 600, never printed). Then it seeds the reference data into Postgres (`python -m backend.seed_refdata` in a one-off backend container; a new stack has no MongoDB and no `MONGO_URI`, so the command's check for unimported Mongo data has nothing to read): the allowed origins, which the API's CORS and the post-sign-in redirect trust, and the Google Forms provider (enabled with `./deploy.sh googleform`). The origins are the web app's public addresses, `HTTP_SCHEME` (default `https`) with `DASHBOARD_DOMAIN` and `FORM_DOMAIN`, read from `.env.webapp` (else `.env.deployment`). With neither domain set the stack is taken for a local one: the origins are the local web app ports (`http://localhost:3000`, `3001`, `3002`), or the origin of `API_CLIENT_URL` when that is not a local address, never localhost on a stack with a public address. This runs only on a new stack (while `BC_FIRST_RUN_PENDING` is in `.env`; a failed seed stops the deploy before the services start, and the next run seeds again), and each table only while it is empty: an upgraded stack imports its reference data from Mongo instead (docs/postgres-cutover-runbook.md). Origins added later (a verified custom domain) are added by the application. Then the services start. Last it shows a one-time setup token on the console only (`./deploy.sh setup-token --new` shows another while setup is not finished; it needs a terminal). The token is in no container log: the one-off container is removed when the command ends.

**A database that already holds data is never bootstrapped.** The two stores are checked in two places. The Postgres side (users, responses) is counted by `bootstrap-keys` itself. The Mongo side is **not** counted by `bootstrap-keys` in a `deploy.sh` run (its one-off container holds the admin database role and nothing else, never the Mongo root credentials, so the command's own Mongo check does not run there); `deploy.sh` decides it explicitly instead: a Mongo volume of this stack (found under the project name compose uses: the shell's or the root `.env`'s `COMPOSE_PROJECT_NAME`, else the directory name) or a `MONGO_URI` in `.env` or `.env.deployment` (an external Mongo it cannot look into) means the stack may hold data, and it never generates keys. In every such case `deploy.sh` stops before any service starts, stores no keys and says so: a new keyset could not read what the old one encrypted. Put the keys the stack has used in `.env` (`AUTH_JWT_SECRET`, `AUTH_AES_HEX_KEY`, `MASTER_ENCRYPTION_KEYSET`) and run `./deploy.sh` again; it imports them (see `settings-import`). Volumes found under a project name other than the one compose will use (say `COMPOSE_PROJECT_NAME` added to `.env` after the stack was created under the directory's name) are refused with the name to set, and no database password is generated while any volume of the stack exists, because those passwords are read only when a volume is created.

**Which services read which env file.** Only the four services that read the settings store (`backend`, `jobs-worker`, `auth`, `integrations-googleform`; they hold the master key, so they can read every stored value anyway) get `.env.deployment` as their `env_file`. The Temporal worker (it drives a browser on user-supplied URLs) and the public webapp each get an env file of their own (`.env.worker`, `.env.webapp`, mode 600, git-ignored) holding only what that service reads, so a bug in the browser or the webapp cannot expose Stripe, Google or mail secrets, the Mongo credentials or any key. `deploy.sh` creates each file once from the lines of `.env.deployment` that service reads (empty values left out) and never changes it afterwards: edit those files for those services, not `.env.deployment`. `.env.deployment` itself is your own file and is not tracked: `deploy.sh` creates it from the template `.env.deployment.example` (mode 600) when it is missing, says so, and never overwrites an existing one. Running `docker compose` without `deploy.sh`? All three env files are optional for rendering (Compose 2.24 or newer); create them yourself (`(umask 077; cp .env.deployment.example .env.deployment)`). The lists live in `deploy.sh` (`webapp_env_keys`, `worker_env_keys`) and a test compares them with `docs/settings-inventory.md`. The Typeform integration was removed in 4.1: an `.env.typeform` left by an earlier release is no longer used (delete it when you no longer need it).

**Services `deploy.sh` starts.** Every deployment starts the webapp, backend, auth, the Temporal worker, Temporal and its database, Umami and its database, nginx, **the admin service, the jobs worker (it consumes the `default` queue: `delete_user` and `delete_response`), the document sandbox and the task runner**, plus the Google Forms integration when asked for (`./deploy.sh googleform`) and Polis with single sign-on. `./deploy.sh typeform` and `./deploy.sh both` (from before the Typeform removal in 4.1) are refused with exit code 2 before anything is changed. MongoDB is not part of a 4.1 stack: it starts only under the `legacy-mongo` compose profile, once, while `deploy.sh` imports a 4.0 stack's data into Postgres (docs/postgres-cutover-runbook.md, "Upgrading to 4.1"), and is stopped and its container removed afterwards; its volume is kept. `deploy.sh` warns when an `integrations-typeform` container from an earlier release still exists; it never removes it. `./deploy.sh print-services [preference]` prints the list; a test runs it through `docker compose up --dry-run`. The first-sign-in notice and the setup token are shown only once the admin service reports healthy. If a first run stops after the keys were stored (a failed start, a closed terminal), the next run still shows the master key fingerprint and the notice (`BC_FIRST_RUN_PENDING` in `.env` marks it until shown).

**The Temporal worker and the actions executor** stay off the store. The worker runs a browser on user-supplied URLs, so it gets neither the master key nor a database role; it keeps `API_KEY` (the backend's `TEMPORAL_API_KEY`) and `AES_HEX_KEY` (the stack's `AUTH_AES_HEX_KEY`) in its environment. `settings-drift` compares both with the store. Rotating `AUTH_AES_HEX_KEY` or `TEMPORAL_API_KEY` therefore also means changing the worker's copy in `.env` until a separate worker key exists.

**`deploy.sh` subcommands** (they need the stack's database running): `settings-import [--dry-run] [--prefer SERVICE]`, `settings-drift`, `settings-prune [--apply] [--swap]` (`--typeform` and `--no-typeform` are accepted and ignored), `settings-env-export --keys A,B --out FILE`, `settings-set`, `settings-clear`, `settings-restore`, `settings-history`, `settings-verify`, `master-key-fingerprint` and `setup-token [--new]`: each runs the host command of the same name (table above) in a one-off container. `settings-import` reads `docker compose config --format json` on standard input, never from a file.

| `GET /internal/admin-tasks/case-duplicate-accounts`, `POST .../{id}/drop` | `task-runner` (`ADMIN_TASKS_BACKEND_URL`) | `ADMIN_TASKS_API_KEY` in `X-Admin-Tasks-Key` |
| `POST /temporal/delete/submissions/{id}`, `PATCH /template/{id}/preview`, `DELETE /auth/user` | Temporal worker (`SERVER_URL`) | `TEMPORAL_API_KEY` in `api-key` (the worker's `API_KEY`) |
| `PATCH /temporal/forms/{form}/actions/{action}/secrets`, `PATCH /workspaces/{ws}/forms/{form}/action/{action}/update` | actions executor (`SERVER_URL`) | the same |

The key is not their only guard. The backend also listens on `API_INTERNAL_PORT` (8001), which
is never published or proxied, and refuses these routes with a plain 404, before it looks at any
key, when the request did not come from inside the stack:

- **Admin-task routes**: the internal listener only, always. Without one (`API_INTERNAL_PORT=0`)
  they are unreachable.
- **Worker routes**: `API_INTERNAL_ROUTES` decides. `direct` (the default, for the transition)
  also accepts them on the public port 8000 for a direct request from a loopback or private
  address (10/8, 172.16/12, 192.168/16, fc00::/7). `internal_port` accepts the internal listener
  only. While the mode is `direct` the backend logs a warning at startup. `direct` is a
  transition setting: a later release makes `internal_port` the default.
- **Any port**: a request carrying a proxy header (`X-Forwarded-For`, `X-Real-IP`, `Forwarded`,
  `X-Forwarded-Proto`/`-Host`, `CF-Connecting-IP`, `True-Client-IP`, `X-Client-IP`,
  `X-Cluster-Client-IP`, `Fastly-Client-IP`, `X-Envoy-External-Address`, `X-Azure-ClientIP`,
  `Via`, ...; any case) is refused. The task runner and the workers never send one.

The listener is chosen by the socket the request arrived on, not by a header, so it cannot be
faked from outside. Both settings are environment only (`docker-compose.deployment.yml` passes
them from the root `.env`).

**Upgrading.** `deploy.sh` and the compose file point the task runner at
`http://backend:8001/api/v1`. The worker's `SERVER_URL` comes from `.env.deployment`: change it
to `http://backend:8001/api/v1` there (the example file has it), run `deploy.sh`, check that
imports, scheduled response deletion and account deletion still work, then set
`API_INTERNAL_ROUTES=internal_port` in the root `.env` and deploy again. A stack deployed without
`deploy.sh` (Docker Swarm, Kubernetes) makes the same changes in its own stack file: the backend
needs nothing new (the listener starts by default); point `SERVER_URL` of the worker and the
actions executor and `ADMIN_TASKS_BACKEND_URL` of the task runner at port 8001 of the backend
service, then switch to `internal_port`.

**Your own reverse proxy.** Whatever sits in front of the API:

- Never publish or proxy port 8001. In Swarm, do not add it to the service's `ports`; services
  on the same overlay network reach it without that.
- Route to port 8000 only, and make the proxy add `X-Forwarded-For` (Traefik, Caddy, Cloudflare
  and most load balancers do by default; nginx needs `proxy_set_header X-Forwarded-For
  $proxy_add_x_forwarded_for;`). In `direct` mode that header is what tells a proxied request
  from a worker's: a proxy that adds none and connects from a private address passes for an
  in-stack caller. `internal_port` does not depend on it.
- `direct` relies on two things: every proxy in front of port 8000 adds a forwarding header, and
  no path to port 8000 rewrites an outside client's address to a private one. Several common
  paths do rewrite it: Docker's userland-proxy (an IPv6 client of a published port arrives as the
  bridge gateway, 172.x.0.1), a proxy on the host that adds no `X-Forwarded-For` (it arrives as
  127.0.0.1), and Swarm's ingress mesh (it arrives as an overlay address, 10.x). Through any of
  them an outside caller passes the edge check and only the key stops it.
- So **Swarm or any ingress-mesh stack, and any stack where port 8000 can be reached from
  outside the host (published directly, as `docker-compose.deployment.yml` does, or behind a
  proxy), MUST use `API_INTERNAL_ROUTES=internal_port`** once its workers call port 8001.
  `internal_port` decides by the socket the request arrived on, so none of these rewrites
  matter.

The SCIM webhook (`POST /scim/webhook/{directory}`, called by Polis) is not one of these routes:
each event is signed with its directory's own secret, and Polis may run outside the stack.

## Upgrading to 4.0

This is the guide for an operator who runs a 3.x stack with `deploy.sh` and moves it to
4.0. It covers what changes, the steps in order, the behaviour changes, what the
migrations touch, how to roll back, what is not solved yet, and a checklist for after the
deploy. The release notes are in [CHANGELOG.md](../CHANGELOG.md). Allow a maintenance
window: the deploy recreates every service and runs migrations.

### What changes

- **Keys and settings move into a settings store.** The stack's keys (`AUTH_JWT_SECRET`,
  `AUTH_AES_HEX_KEY`, `AUTH_INTERNAL_NOTIFY_KEY`, `TEMPORAL_API_KEY`, the response keyset)
  and the settings the services read live in a signed, encrypted store in the
  application Postgres, edited in the admin portal or with host commands. The backend, the
  jobs worker, auth and the Google integration read it (`SETTINGS_STORE=required`). On an
  upgrade `deploy.sh` imports what your files hold.
- **Four values matter:**

  | Value | Where | Who |
  |---|---|---|
  | `PLATFORM_ADMIN_EMAILS` | root `.env` | you: the super admins' addresses, comma-separated. Without it the portal stays off (the bare gate) and `deploy.sh` says so |
  | `ADMIN_ALLOWED_IPS` | root `.env` | you, only when you reach the portal from another address than the host (default `127.0.0.1/32`). In the default layout it restricts nothing that comes through the published port: see "Network" |
  | `SETTINGS_MASTER_KEY` | root `.env` | generated on the first 4.0 deploy and never overwritten. **You back it up, separately from the server.** It cannot be recovered and nothing stores a copy: without it the settings store, the second-factor secrets and the audit log's verification are lost. `./deploy.sh master-key-fingerprint` prints a short id of it, to write down with the backup (a restored key with another fingerprint is the wrong key) |
  | `DATABASE_URL` | not an operator value | compose builds each service's URL from its own role password; pointing the bundled stack at an external Postgres is not supported |

- **An admin portal replaces the public metrics page.** It is a separate service,
  published on `127.0.0.1:8100` only. Reach it with an SSH tunnel
  (`ssh -L 8100:127.0.0.1:8100 <host>`, then `http://localhost:8100`). **Never put a
  reverse proxy in front of port 8100** and never publish it on another interface: any
  local process and any proxy on the host passes its address check. See "Network" for what
  `ADMIN_ALLOWED_IPS` does and does not protect. Super admins are the addresses in
  `PLATFORM_ADMIN_EMAILS`; sign-in is a mailed code plus an authenticator, so set
  `MAIL_SMTP_SERVER` and `MAIL_SENDER` (and `MAIL_USER` / `MAIL_PASSWORD` if the server needs
  them) in the root `.env`, or use the setup wizard (step 3), which works without mail.
- **`TRUSTED_PROXIES` must be set behind a reverse proxy or load balancer.** The backend no
  longer believes `X-Forwarded-For` from any private-network peer. Put the proxy's
  address(es) or CIDR(s), comma-separated, in the root `.env`; without it every visitor
  looks like the proxy and shares its rate limits.
- **`PLATFORM_ADMIN_EMAILS` has a second job.** It still grants the `ADMIN` role after a
  verified sign-in in the public app (the operator-only endpoints check it), so keep it set.

### Before you start

1. **Back up**, and keep the copies off the server. They hold your data, encrypted with
   the keyset you use now, so treat them like the live data:

   ```bash
   umask 077
   docker compose -f docker-compose.deployment.yml exec -T app-postgres \
     pg_dump -U bettercollected -Fc bettercollected > postgres-before-4.0.dump
   docker compose -f docker-compose.deployment.yml exec -T mongodb \
     mongodump --username root --password root --authenticationDatabase admin --archive --gzip \
     > mongo-before-4.0.archive.gz
   cp .env .env.before-4.0; cp .env.deployment .env.deployment.before-4.0
   ```

   (Use your own Mongo credentials if you changed them; skip the Mongo dump if no data is
   in Mongo. The copies of the env files hold secrets: keep them private and delete them
   when the stack runs well.) Test that you can restore one.
2. **Check the host.** Docker Compose v2 (`docker compose`; the importer reads
   `docker compose config --format json`, and the compose file uses optional env files,
   which need Compose 2.24 or newer). The bundled `app-postgres` image is Postgres 16.
3. **Keep your keys.** If `.env.deployment` holds your own `AUTH_JWT_SECRET`,
   `AUTH_AES_HEX_KEY` or `MASTER_ENCRYPTION_KEYSET`, they are copied and imported. A stack
   that holds responses must keep its `MASTER_ENCRYPTION_KEYSET`: `deploy.sh` stops and asks
   for it rather than generate a new one that could not read them.
4. **Set in the root `.env`** (create it if it is not there): `PLATFORM_ADMIN_EMAILS`,
   `TRUSTED_PROXIES` if you run a proxy or load balancer, and the `MAIL_*` values for the
   sign-in mail. Leave `ADMIN_ALLOWED_IPS` alone unless you need it.
5. **Images.** `docker-compose.deployment.yml` runs the `bettercollected/<service>:nightly`
   images and `deploy.sh` pulls them on every run. Check out the release tag so the compose
   file, `deploy.sh` and the scripts are the release's.
6. **Keep `.env.deployment` across the update.** From 4.0 the repository no longer tracks
   `.env.deployment`. It ships the template `.env.deployment.example` instead, and
   `.env.deployment` is git-ignored: `deploy.sh` creates it from the template (mode 600)
   only when it is missing, and never overwrites it. Because the tracked file is deleted
   upstream, updating a 3.x checkout (`git pull`, or `git checkout` of the release tag)
   does this to your copy:
   - **unchanged since you cloned:** git deletes it, without a warning. That copy holds the
     values the 3.x repository shipped, including the published response keyset; a stack
     whose responses are encrypted with it needs it for the import (without it `deploy.sh`
     recreates the file from the template and then stops, asking for
     `MASTER_ENCRYPTION_KEYSET`).
   - **changed (your values in it):** git refuses and changes nothing ("Your local changes
     to the following files would be overwritten by merge", or "by checkout").

   So, in both cases, before you update:

   ```bash
   cp -p .env.deployment .env.deployment.mine   # your copy; git ignores it
   git checkout -- .env.deployment              # undo your edits, so git can remove the file
   git pull                                     # or: git fetch --tags && git checkout <release tag>
   mv .env.deployment.mine .env.deployment      # your file again, now ignored by git
   ```

   `git status` no longer lists `.env.deployment`. If the file is gone and you have no copy,
   take it from the backup of step 1 (`.env.deployment.before-4.0`). If you committed your
   values on a local branch, the pull stops with a modify/delete conflict on
   `.env.deployment` and leaves your version in place: keep it and stop tracking it with
   `git rm --cached .env.deployment` and `git commit`.

### Steps

1. **Check out the release** (keeping your `.env.deployment`, step 6 above) and run
   `./deploy.sh` with the same preference as before
   (`./deploy.sh` or `googleform`; to 4.1 and later, `typeform` and `both` are refused: use
   `googleform` for `both`). In order, it:
   - generates what is missing in the root `.env`, once and never overwriting: the database
     role passwords, `UMAMI_APP_SECRET`, `SETTINGS_MASTER_KEY` and the Temporal worker's
     two keys (the Temporal, Umami and Mongo database passwords only for a new volume: an
     existing volume keeps its password);
   - creates `.env.webapp`, `.env.worker` and `.env.typeform` once from the lines of
     `.env.deployment` those services read (check them afterwards, see "Behaviour changes");
   - pulls the first-party images, starts `app-postgres`, runs the roles script, the admin
     schema's migrations, the application, jobs, auth and (if deployed) Google migrations,
     and the roles script again (a failed migration stops the deploy);
   - **imports** the keys and settings your files carry: it copies your own keys from
     `.env.deployment` into the root `.env` (a published `AUTH_JWT_SECRET` or
     `AUTH_AES_HEX_KEY` is not copied and a new one is generated; a published keyset is
     kept, because responses depend on it), generates `AUTH_INTERNAL_NOTIFY_KEY` and
     `TEMPORAL_API_KEY` if you had none, reads `docker compose config --format json`
     (piped, never written to disk) and imports each setting once. It never overwrites a
     stored value and prints only names and counts;
   - **compares** the store with the files (`settings-drift`) and stops if any value differs;
   - starts every service, replaces Umami's built-in login, and prints notices.

   It stops, before any service starts, when:

   | The message | What it means and what to do |
   |---|---|
   | `Volumes of a stack named '...' exist, but docker compose will use the project name '...'` | The stack was created under another compose project name. Set `COMPOSE_PROJECT_NAME=<that name>` in `.env` and run again |
   | `MASTER_ENCRYPTION_KEYSET is not set, and this stack already holds data` | Copy the `MASTER_ENCRYPTION_KEYSET` line from your previous `.env.deployment` into the root `.env` |
   | `SETTINGS_MASTER_KEY is not set in .env, but this stack has run before` | Your files carry none of the stack's keys. If a settings store exists, restore the key you backed up; otherwise add `SETTINGS_MASTER_KEY` to `.env` |
   | `conflict <key> ...` in the import | Two services carry different values for one setting. `./deploy.sh settings-import --dry-run` shows them; `./deploy.sh settings-import --prefer SERVICE` picks one. Nothing is chosen for you |
   | `refused <key> too_short`, `low_entropy`, `weak_secret` or `bad_keyset` | A legacy secret is too weak or malformed to be stored (see "Behaviour changes"). Replace it in the file named, then run again |
   | `The store and the files differ` | Fix the differing values (the output names them) and run again |

   A refused ordinary value (for example an `http://localhost` URL, which the registry
   will not store) is a warning: it stays an environment value.
2. **Back up `SETTINGS_MASTER_KEY` now** and write down `./deploy.sh master-key-fingerprint`.
   On an upgrade `deploy.sh` does not print the fingerprint (it does on a new install).
3. **First sign-in.** `deploy.sh` shows a setup token only on a new install, so on an
   upgrade run `./deploy.sh setup-token --new` from a terminal once the admin service is
   healthy (`docker compose -f docker-compose.deployment.yml ps admin`). Open an SSH tunnel,
   then `http://localhost:8100/setup`, enter the token and one address from
   `PLATFORM_ADMIN_EMAILS`, enrol an authenticator, save the ten recovery codes, optionally
   save the sign-in mail settings (a test mail must arrive first) and acknowledge the
   master key fingerprint. If mail already works you can instead open the portal and sign in
   with a mailed code, which leads to the same enrolment. Every admin enrols their own
   factor. If the authenticator and the recovery codes are both lost, only the host can
   reset the factor: `python -m backend.admin reset-factor --email <address> --yes`.
4. **Check the stack** with the checklist below.
5. **Prune the old values** when the stack runs well. An environment value wins over the
   store, so a stale value in `.env` or `.env.deployment` silently overrides a change made
   in the portal, and a rotated key would be ignored by every service that still has the old
   one in its environment. `./deploy.sh settings-prune` shows what would be removed;
   `./deploy.sh settings-prune --apply --swap` does it and leaves private
   `.env.pre-v4.<time>` and `.env.deployment.pre-v4.<time>` backups (they hold the old
   secrets: delete them when you no longer need them). Prune never removes a setting whose
   value differs from the store, and keeps in the files what something outside the store
   reads: the SSO values, `MAIL_*` (the admin sign-in mail), and the Typeform service's three
   keys when it is deployed (`--typeform` / `--no-typeform` override the detection). Two root
   `.env` aliases are not setting names and are never pruned: `TRUSTED_PROXIES` and
   `STRIPE_REDIRECT_URL`; remove them yourself once the import has run, and manage the
   setting in the portal.
6. **Rotating the response keyset is not part of this upgrade.** If your stack ran with the
   keyset that was published in this repository, services log a warning at startup until you
   rotate it. After the upgrade, and after pruning, rotate it with the portal's Tasks pages
   (`keyset.add_key`, restart, `keyset.promote`, restart, `keyset.reencrypt`,
   `keyset.verify`, `keyset.drop_old`, each mutating step after a dry run) as described in
   [response-keyset-rotation.md](response-keyset-rotation.md). Take a fresh backup first.

### Behaviour changes

- **`DEBUG` and the internal APIs' docs are off.** Neither is set in the compose file or
  `.env.deployment` any more (a pinned value would win over the portal). If you relied on
  `/docs`, `/redoc` or HTML tracebacks, set `API_DOCS_ENABLED=true` or `DEBUG=true`
  deliberately (portal, or `.env.deployment`) and turn them off afterwards. 422 answers no
  longer echo the rejected input. The backend health check probes the public API document
  instead of `/api/v1/docs`; custom orchestration that probed `/docs` needs the same change.
- **Weak or malformed legacy secrets are refused on import.** Published `AUTH_JWT_SECRET` and
  `AUTH_AES_HEX_KEY` values are replaced by new random ones, and the services refuse to start
  with an empty or published one. A short or low-entropy `AUTH_JWT_SECRET` of your own, an
  `AUTH_AES_HEX_KEY` that is not a Fernet key, or a keyset that is not valid is refused with a
  refusal code. **The consequence is one forced rotation:** replacing the JWT secret signs
  everyone out once; replacing the Fernet key makes data encrypted with the old one
  unreadable (reconnect Google Forms and Google Sheets, re-enter form-action secrets,
  regenerate SCIM webhook secrets; running SSO and OAuth sign-ins restart). The published
  response keyset is still accepted, because a new one could not read your responses: rotate
  it afterwards (step 6).
- **The public `/admin/metrics` page and endpoints are gone** (webapp page and menu entry,
  backend `GET /admin/metrics`, auth `GET /admin/metrics`). The metrics are in the portal
  (`/metrics`).
- **`GET /workspaces/{id}/forms/{form_id}/all-submissions` needs the export permission**
  (Owner, Admin and Editor have it; Viewer, Reviewer and Privacy officer do not) instead of
  the read permission. The builder's flow view uses the new `.../submission-paths`, which
  needs only `response.read` and carries no answers. Scripts that called `.../all-submissions`
  with a read-only role need the export permission.
- **Temporal's port 7234 is no longer published.** Its frontend has no authentication and is
  reachable on the compose network only (`docker compose exec temporal temporal ...`).
- **Umami.** The dashboard moved from `0.0.0.0:3003` to `127.0.0.1:3004`; port `3003` is
  nginx and passes only the tracker script and event endpoints, so `UMAMI_SCRIPT_URL`
  (`http://<host>:3003/script.js`) keeps working. A reverse proxy that pointed at 3003 for
  the dashboard must point at 3004 (or use `ssh -L 3004:127.0.0.1:3004 <host>`). The built-in
  `admin`/`umami` login is replaced with a generated password after the first start, and on
  an upgrade when the built-in login still works, stored as `UMAMI_PASSWORD`; to sign in
  yourself run `./deploy.sh settings-env-export --keys UMAMI_USERNAME,UMAMI_PASSWORD --out FILE`
  and delete the file afterwards.
- **The Mongo `seeduser` account is removed** from existing volumes by the seed job, which
  no longer passes a password on a command line.
- **Per-service env files.** The webapp, the Temporal worker and the Typeform service read
  `.env.webapp`, `.env.worker` and `.env.typeform` (mode 600, git-ignored), not
  `.env.deployment`. `deploy.sh` creates each once from the lines of `.env.deployment` that
  service reads and never changes it afterwards: look at them once, put anything else those
  services need into them, and edit them (not `.env.deployment`) from now on.
- **`deploy.sh` starts four more services:** the admin service, the jobs worker, the document
  sandbox and the task runner. `OAUTHLIB_INSECURE_TRANSPORT=1` is no longer in the shipped
  `.env.deployment` (plain-http OAuth redirects need it added deliberately); `AUTH_CALLBACK_URI`
  and `UMAMI_URL` are no longer pinned by the compose file (the first has its code default,
  the second is seeded with the compose-network address), and `TYPEFORM_REDIRECT_URI` and
  `TYPEFORM_SCOPE` come from `.env.deployment`. `.env`, `.env.deployment` and every generated
  or exported env file are mode 600.
- **Flow events older than 13 months are deleted** (`API_FLOW_EVENTS_RETENTION_DAYS`, default
  395; 0 keeps them).
- **Single sign-on (`SSO_*`) and the admin sign-in mail (`MAIL_*`)** stay environment-driven
  in this release, and are kept in the files by `settings-prune`.
- **`.env.deployment` is no longer tracked.** The repository ships `.env.deployment.example`;
  `deploy.sh` creates `.env.deployment` from it (mode 600) when it is missing and never
  overwrites it, and git ignores it. Keep your copy across the update ("Before you start",
  step 6). The four services that read it treat it as optional (Compose 2.24 or newer), so
  `docker compose config` works on a fresh checkout before `deploy.sh` ran.
- **The deploy workflow** still deploys `develop` and `master` to the development and staging
  stacks; only production is deployed from release tags (`vMAJOR.MINOR.PATCH`, optionally
  with a pre-release suffix), and a tag that is not a version tag is refused. Its actions are
  pinned by commit.

### Migrations

`deploy.sh` runs them, in this order, before the services start:

- `postgres/ensure-admin-roles.sh`: creates the admin schema's roles and grants, the two
  platform-count functions and the Health page's revision and outbox functions; idempotent, run before the migrations and again after them (the
  task runner's data roles are granted on tables the other migrations create).
- The **admin** schema's own chain, `0001` to `0017`, as the migration role `bc_admin_mig`.
- The **application** schema: `0013` to `0016` (rate-limit counters, the AI notice stamp on
  responses, the workspace id on responses and deletion requests, API idempotency keys;
  there is no `0012`). Every one is expand-only, so a previous release keeps running on the
  migrated schema. Two of them, `0014` and `0015`, rewrite `app.form_responses` under an
  exclusive lock: a few seconds on fast storage, longer on a large table. Reads and writes of
  responses wait meanwhile, so upgrade at a quiet moment.
- procrastinate's `jobs` schema, **auth** and **google**: no new revisions since 3.4.0, the
  commands run and find nothing to do.

The admin portal, the task runner and the host commands are one image and one version:
deploy them together. The runner's keyset write and audit calls use functions that this
release's migrations create, and the old signatures are dropped.

### Rolling back

- **Back to the files, keeping 4.0:** set `SETTINGS_STORE=off` in the root `.env` and run
  `./deploy.sh` again. The services read their environment again, the store is kept and
  nothing in it is deleted. Before pruning, the values are still in `.env` and
  `.env.deployment`. After pruning, put the `.env.pre-v4.*` and `.env.deployment.pre-v4.*`
  backups back (or `./deploy.sh settings-env-export --keys ... --out FILE` for the values you
  need), then set `off`.
- **Back to 3.x images:** a release that predates the store does not use it at all. Check out
  the old tag, restore the pre-prune backups so the old files hold their values, and redeploy.
  A 3.x tag tracks `.env.deployment` again, and git replaces an ignored file of that name
  without asking: checking out the old tag overwrites your `.env.deployment` with the file
  that release shipped. Copy it first and put it back afterwards
  (`cp -p .env.deployment .env.deployment.mine`, check out, `cp .env.deployment.mine
  .env.deployment`); going forward again is the update in "Before you start", step 6.
  Migrations are expand-only, so the old images run on the migrated schema. Data written under
  keys that changed during the upgrade (a Google connection you reconnected, a form-action
  secret you re-entered) is not readable with the old key.
- Restoring the database from a backup into a running 4.0 stack: the services keep a signed
  snapshot of the highest settings revision they accepted and, with `SETTINGS_STORE=required`,
  refuse to start on an older store. After a restore you meant to do, remove the snapshot
  volumes and restart (see "Rollback and wipe protection").

### Known limits

- The Temporal, Umami and Mongo databases keep the passwords of an **existing volume** (a new
  volume gets generated ones). Mongo's root account on an old volume stays `root`/`root`, on
  the compose network only; changing any of them is manual (see "Internal credentials and
  ports").
- **An external `DATABASE_URL` is not supported** by the bundled compose file.
- **Compose v2 is required** (see "Before you start"); `deploy.sh` still falls back to
  `docker-compose` when `docker compose` is missing, but the import needs
  `docker compose config --format json`.
- **The actions executor** is not run by this repository's compose files. Its environment is
  whatever the stack that deploys it passes: keep `SETTINGS_MASTER_KEY` and other services'
  `DATABASE_URL`s out of it and check it against `temporal/actions-executor/.env.example`. It
  still reads `API_KEY` and `AES_HEX_KEY` itself, and runs creator code with `exec` (not a
  sandbox), so give it nothing else.
- **Rollback protection has a gap:** a validly signed older store is accepted by a service that
  starts with no snapshot (volume gone, `docker compose down -v`). The admin integrity check is
  the alarm; keep and back up the snapshot volumes with the master key.
- **The Temporal worker runs Chromium with `--no-sandbox` as root** on user-supplied URLs. It
  holds no secret beyond `API_KEY` and `AES_HEX_KEY` (no master key, no database role) and drops
  all capabilities.
- The SSO and mail settings are not in the store yet.
- Third-party images with state (`mongo`, `temporalio/auto-setup`, Umami) are not pinned.
- With SSO on, Polis shares a network with the services that call it (see `docs/sso.md`).

### Checklist after the deploy

On the host:

- [ ] `docker compose -f docker-compose.deployment.yml ps`: `admin` and `document-sandbox`
  are healthy, `task-runner` and `jobs-worker` are running.
- [ ] `./deploy.sh master-key-fingerprint` is written down and `SETTINGS_MASTER_KEY` is backed
  up elsewhere.

## Task runner: the responses data tasks

The `task-runner` service (backend image, no published port, own database role)
runs the tasks the portal lists. Two of them work on stored responses:

| Task | Does | Refuses with |
|---|---|---|
| `responses.check_undecryptable` | read-only: counts stored values that carry the ciphertext prefix but do not decrypt, per store and field (no ids, no values) | `store_not_configured`, `keyset_missing`, `keyset_unreadable`, `store_unreachable`, `store_empty` |
| `responses.backfill_workspaces` | stamps responses and deletion requests that predate `workspace_id`; a dry run first (required), resumable, idempotent; ambiguous records (a form linked to several workspaces with nothing to authenticate them) are never guessed and stay unstamped | the same codes; the apply also `forms_import_incomplete` while a Mongo store is covered and the 4.0 forms import is not complete (complete the forms import, backfill and verify, first) |

Both need the data stores and the keyset in the runner's environment. The
compose service passes them from the root `.env`, and they are empty by default
(the tasks then refuse; nothing else changes):

| Variable | Meaning |
|---|---|
| `TASK_RUNNER_DATABASE_URL` | Postgres URL of the data role for the `app` schema. It defaults to `bc_tasks_data_app` (below), built from `BC_TASKS_DATA_APP_PASSWORD`; set it only to point at another dedicated role, never the backend's: that would give the runner the whole app schema next to the keyset |
| `TASK_RUNNER_GOOGLE_DATABASE_URL` | the same for the Google credentials (`google` schema); defaults to `bc_tasks_data_google` from `BC_TASKS_DATA_GOOGLE_PASSWORD`, never the integration's role |
| `TASK_RUNNER_MONGO_URI` / `TASK_RUNNER_MONGO_DB` | Mongo, while Mongo still holds responses (`TASK_RUNNER_MONGO_DB` defaults to `bettercollected_backend`). A read-only Mongo user is the recommended deployment for the check and for dry runs |
| `TASK_RUNNER_KEYSET` | the response keyset for the read-only `responses.*` tasks and `keyset.verify` when it is not in the settings store; it never goes to a file or a log. The `keyset.*` tasks that change or re-encrypt ignore it and use the settings store only |
| `DB_WRITE_MODE`, `DB_WRITE_MODE__RESPONSES` | the services' write mode (from the root `.env`; keep it equal to the services' and change it with them during the move to Postgres). It decides the stores `stores: auto` covers (every store the services still write) and the primary store of `keyset.drop_old`; unset, the services' default applies (`mongo` while the backend has groups on Mongo), as on a fresh stack where the services run on it too; a value that is not a write mode refuses with `write_mode_unknown`. The Google credentials need none: they are in Postgres only since 4.1 |
| `TASK_RUNNER_GOOGLE_MONGO_DB` | the Google Forms integration's Mongo database (default `bettercollected_googleform`) |

`stores: auto` covers every store the services still write for the task's group, as the
runner's `DB_WRITE_MODE*` says (`mongo`: Mongo; `dual` and `postgres_primary_dual`: both;
`postgres`: Postgres), each of which must be configured (else `store_not_configured`), and then
any other store the runner is configured for; never fewer than the services write, so once Mongo
is retired the tasks run on Postgres alone (unset `TASK_RUNNER_MONGO_URI`). With the write mode
unset `auto` follows the services' default (`mongo` while the backend has groups on Mongo, so the
runner then needs `TASK_RUNNER_MONGO_URI`); with one it cannot read it refuses
(`write_mode_unknown`). `mongo`, `postgres` or `both` name the stores,
need no write mode, and refuse if one is missing. `keyset.drop_old` does not follow `auto`: it
scans both stores, each configured, or refuses, unless the operator ticks `mongo_retired` (signed and
audited; accepted only with the runner's write mode `postgres` for every group), which scans
Postgres alone (docs/response-keyset-rotation.md, "The store rule"). The scripts `backend/scripts/check_undecryptable_values.py`
and `backend/scripts/backfill_response_workspaces.py` stay as command-line
tools (the backfill gained `--workspace-id` and `--form-id`), sharing the same code.

### The runner's data roles: `bc_tasks_data_app` and `bc_tasks_data_google`

`postgres/ensure-admin-roles.sh` (run by `deploy.sh` before the migrations and again after
them) creates two login roles, one per owning schema, with the passwords
`BC_TASKS_DATA_APP_PASSWORD` and `BC_TASKS_DATA_GOOGLE_PASSWORD` (generated once into the root
`.env`, URL-safe characters only, never printed). They are separate from `bc_tasks`, which holds
the runner's own state and the settings store. Why two: an UPDATE runs the table owner's triggers
and generated-column helpers with the updater's privileges. One role over `bc_app`'s and
`bc_google`'s tables would let either owner plant code that a re-encryption run executes with
access to the other's table. Each role holds no more than the owner of its schema already has, has
`search_path = pg_catalog`, and has USAGE on its own schema only. Column-level grants, nothing else:

| Role | Table | SELECT | UPDATE |
|---|---|---|---|
| `bc_tasks_data_app` | `app.form_responses` | `id`, `form_id`, `response_id`, `workspace_id`, `doc` | `doc`, `_bc_checksum` |
| | `app.responses_deletion_requests` | the same columns | `doc`, `_bc_checksum` |
| | `app.workspace_forms` | `id`, `form_id`, `workspace_id`, `doc` | none |
| `bc_tasks_data_google` | `google.oauth_credentials` | `id`, `user_id`, `doc` | `doc`, `_bc_checksum` |

No INSERT, DELETE, TRUNCATE or TEMPORARY; nothing in `admin`, `tasks`, `settings`, `auth` or `jobs`.
The only function granted to either role is `google.purge_unencrypted_credentials(apply)`
(`bc_tasks_data_google`, for the task of the same name, below): a definer function owned by the
NOLOGIN role `bc_tasks_purge_google`, which holds DELETE on `google.oauth_credentials` alone.
The grants are in the roles script, not in a migration, because the tables belong to other roles.
`tests/admin/tasks/test_data_role.py` pins the exact privilege set per role, that neither role can
reach the other's schema or anything its owner owns, and that a hostile trigger of either owner
gets nothing from the other.

Mongo, while it still holds responses: give the runner a dedicated user. For the check, `verify`
and dry runs a read-only user is enough (`read` on the responses database and the Google
integration's database). `responses.backfill_workspaces`, `keyset.reencrypt` and the other writing
tasks need `readWrite` on exactly `form_responses` and `Oauth2CredentialDocument` (the
credentials), and `read` on `workspace_forms`. Put its URI in `TASK_RUNNER_MONGO_URI`.

### Keyset tasks

`keyset.add_key`, `keyset.promote`, `keyset.reencrypt`, `keyset.verify` and `keyset.drop_old`
rotate `MASTER_ENCRYPTION_KEYSET`; the order and every guard are in
[response-keyset-rotation.md](response-keyset-rotation.md). They hold the locks `keyset` and
`responses.encryption`, so only one of them runs at a time.

### Google credentials without a user id

`google.purge_unencrypted_credentials` deletes the Google Forms integration's stored credentials
that have no user id, or whose tokens are stored readable: the one-time cleanup of
[postgres-cutover-runbook.md](postgres-cutover-runbook.md) ("Google credentials without a user
id"), with exactly its filters (Mongo `Oauth2CredentialDocument`: `user_id` missing, null or
empty, or `credentials.token` / `credentials.refresh_token` present; Postgres
`google.oauth_credentials`: `user_id` empty or null, or `credentials` a JSON object without
`$binary`).

- **Dry run first** (required): the count per store; nothing changes, both stores are opened
  read-only.
- **Apply** (confirmation code, like every changing task): Mongo first, then Postgres, whatever
  the services' primary store, so that neither store copies a row back to the other. One audit
  row per store (`task.google.purged`, target `google_oauth` / the store) with the matched and
  deleted counts. Running it again deletes nothing.
- **Stores:** `auto` follows the store rule above (group `google`, written to Postgres alone from
  4.1, so `auto` is Postgres plus Mongo when the runner has a Mongo connection); `mongo`,
  `postgres` or `both` name them. An apply must cover every store the services still write, and
  Mongo whenever the runner has a Mongo connection, else it refuses with `stores_incomplete`:
  neither store keeps a deletion tombstone, so a row left in Mongo would come back with the next
  backfill (on 4.1 the import from 4.0, `python -m googleform.migrate backfill`, still copies
  whatever Mongo holds) or reconcile. A dry run may count a single store. Use `auto`.
- **Order on 4.1:** finish the import from 4.0 (backfill, then verify) first, then run the purge.
  A runner without a Mongo connection may apply on Postgres alone; the gate cannot see Mongo
  then, so a purge run before the import has finished is undone by it. Alternatively purge both
  stores on 4.0.10 before upgrading.
- **Counts only** in the result, the events and the audit log: never an id, an email or a token.
- **Least privilege:** Mongo through the runner's Google Mongo connection (`MONGO_URI` /
  `TASK_RUNNER_GOOGLE_MONGO_DB`), `deleteMany` with the filter above (the user needs `readWrite`
  on `Oauth2CredentialDocument`). Postgres through `bc_tasks_data_google`, which has no DELETE: it
  calls `google.purge_unencrypted_credentials(apply)`, a `SECURITY DEFINER` function with a pinned
  `search_path` that holds the filter and returns the count. Its owner `bc_tasks_purge_google` is
  NOLOGIN and holds DELETE on that table alone; `postgres/ensure-admin-roles.sh` makes both.
  Without the function the task refuses with `purge_function_missing`.

### Accounts whose emails differ only in case

`auth.resolve_case_duplicate_accounts` resolves the accounts whose emails are equal ignoring case
(`Jane@Example.com` and `jane@example.com`). Older versions let one address hold several such
accounts; 4.1's auth makes `auth.users` unique by `lower(email)` and does not start while any
remain, so run this task on 4.0.x before upgrading. For each group:

From 4.1 the task finds nothing in a migrated database: auth's revision 0005 refuses to run while
such accounts exist, and the index then keeps new ones out. On 4.1, accounts still in a 4.0 Mongo
being imported are caught by `python -m auth.migrate preflight` (it fails and counts them as
`case_variant_keys` / `case_variant_documents`), and `backfill` stops `users` on the first one.
Resolve them with this task on 4.0.11 or later, before the import (see
docs/postgres-cutover-runbook.md, "Accounts whose emails differ only in case"). The task stays in
the 4.1 catalog so that a run on a database that still had such accounts reports 0 groups, and the
4.0 and 4.1 task lists match.

1. An account **without forms** is dropped.
2. If **exactly one** account has forms, it is kept.
3. If **none** has forms, the one **created last** is kept and the others are dropped. "Created"
   is the account id's (ObjectId) timestamp, because some account documents have no
   `created_at`; at the same second, the larger id stays.
4. If **two or more** have forms, those are not touched: the group is listed for manual handling
   (move what the person needs, then delete the other account through the product). The
   formless accounts in that group are still dropped (rule 1).

There is no other guard (plan, billing, memberships elsewhere, last sign-in): the rules apply as
stated. "Has forms" means the account's deletion would take at least one form: a
`workspace_forms` row in a workspace the account owns (`workspaces.owner_id`), or one it imported
(`workspace_forms.user_id`), counting distinct form ids, of any provider.

- **Dry run first** (required): one event per account, numbered by group (`group` 1, 2, ...):
  the decision as the event code (`keep`, `drop`, `manual`), the forms count, and as ids the
  account id and its created time; then the totals (`counted`). Nothing changes.
- **Apply** (confirmation code): each `drop` account is deleted through the product's account
  deletion, the same workflow as a user's own request (`AuthService.add_workflow_to_delete_user`:
  sessions revoked, then the deletion job removes the account's workspaces and forms, its
  memberships, its integration credentials (the Google credential purge included), its auth
  account and billing customer, in every store the services write). The API evaluates the
  account's group again right before (a change since the dry run is honoured: an account that
  now has forms is not dropped, `drop_skipped` / `changed`). If the product's deletion refuses
  (the account is the billing owner of a workspace with other owners), the drop is skipped
  (`refused`) and the account is left for manual handling. The task then waits up to 10 minutes
  for the deletion jobs and reports what remains: one `remaining` event per group left (its
  account ids) and `remaining_groups` / `remaining_manual_groups` in the result. The target is
  0 remaining groups apart from the manual ones. One audit row
  (`task.accounts.case_duplicates_resolved`) with the counts. Running it again drops nothing.
- **Ids and counts only** in the result, the events and the audit log: never an email, not even
  lowercased.
- **Least privilege:** the runner gets no access to the accounts, workspaces or forms for this
  task, and no database grant. It calls the API's internal admin-task routes
  (`/api/v1/internal/admin-tasks/case-duplicate-accounts`, and `.../{id}/drop`), which decide and
  start the deletion; the auth service groups the accounts and returns ids only
  (`GET /users/case-duplicates`, internal key). The runner presents `ADMIN_TASKS_API_KEY` in
  `X-Admin-Tasks-Key`; the backend accepts nothing else on those routes and answers 503 while
  its own `ADMIN_TASKS_API_KEY` is unset, so the routes are off by default. Set the same random
  value (for example `openssl rand -hex 32`) on the `backend` and `task-runner` services;
  `ADMIN_TASKS_BACKEND_URL` (compose: `TASK_RUNNER_BACKEND_URL`, default
  `http://backend:8001/api/v1`, the backend's internal listener) is where the runner reaches the
  API; the routes answer nowhere else ("Internal routes" above). Without them the task
  refuses with `backend_not_configured`, `backend_key_missing` (the API has no key) or
  `backend_key_refused` (the keys differ). Unset the key on both once the task is done.

#### Troubleshooting refusals

A refused run records one of these codes. The task-runner's log has a line per refused call
with the HTTP status (`... was refused: <code> (HTTP status <n>)`); status and code only, never
a body. The backend logs `the auth service call failed (<code>, status <n>)` when its call to
auth is the cause.

| Code | Likely cause | What to check |
| --- | --- | --- |
| `backend_not_configured` | The runner has no `ADMIN_TASKS_API_KEY`, or `ADMIN_TASKS_BACKEND_URL` is not a valid `http(s)` URL | The `task-runner` service's environment |
| `backend_unreachable` | No connection to the API, or it timed out | `ADMIN_TASKS_BACKEND_URL` (compose: `TASK_RUNNER_BACKEND_URL`); that the `backend` service is up and on the runner's network |
| `backend_key_missing` | The API answered 503: its own `ADMIN_TASKS_API_KEY` is unset | Set the key on the `backend` service |
| `backend_key_refused` | The API answered 401/403: the two `ADMIN_TASKS_API_KEY` values differ | The same value on `backend` and `task-runner` |
| `backend_route_missing` | The API answered 404: the URL is not the backend's internal listener (the admin-task routes answer there only), the backend is older than this task, or the URL's path is wrong | That `ADMIN_TASKS_BACKEND_URL` is `http://backend:8001/api/v1` (the internal listener, `API_INTERNAL_PORT`); the backend image version |
| `backend_redirect` | The API answered with a redirect (3xx), which the runner never follows; the log line has the status | `ADMIN_TASKS_BACKEND_URL` is the API's own `http(s)://host:port/api/v1` (not a proxy that redirects, for example to `https`); a task runner from before the exact-path fix requested the routes with a trailing slash and got a 307 (shown then as `backend_unreachable`) |
| `backend_error` | The API answered 5xx or another unexpected status (a 502 from a proxy in front of it, too) | The backend's log at the time of the run |
| `backend_bad_reply` | The API answered 200 with something other than the expected JSON | That the URL reaches the backend, not another service or a proxy page |
| `auth_unreachable` | The API could not reach the auth service (connection or timeout) | The backend's `AUTH_BASE_URL`; that the `auth` service is up |
| `auth_key_refused` | Auth answered 401/403 to the API: the backend's `AUTH_INTERNAL_NOTIFY_KEY` is not the one auth holds | The same `AUTH_INTERNAL_NOTIFY_KEY` on `backend` and `auth` |
| `auth_misconfigured` | The API's `AUTH_BASE_URL` is not a usable URL | The backend's `AUTH_BASE_URL` (compose: `http://auth:8000/api/v1`) |
| `deletion_unavailable` | Apply only: the API could not start an account deletion (the deletion workflow: Temporal, or the jobs worker on Postgres) | The backend's log (`deletion could not be started`, with the error type and status); Temporal or the jobs worker; run the apply again once it is back: accounts already started are skipped |
| `forms_import_incomplete` | The API counts an account's forms in Postgres only (4.1) and the 4.0 forms import is not complete: Mongo's `workspace_forms` holds a link Postgres lacks and no finished backfill of it is recorded (or Mongo, configured, could not be read). Before the import every account would count no forms | Complete the forms import (backfill and verify) first: `python -m backend.migrate --group forms backfill`, then run the task again |
| `auth_error` | Auth answered another error (503: auth has no `AUTH_INTERNAL_NOTIFY_KEY`) or an unreadable reply | The status in the backend's log line; the auth service's log |

A backend from before this change passes auth's failures through as its own status, so with
it an auth problem can still show as `backend_key_missing`, `backend_key_refused` or
`backend_error`; check the backend's log for a failed call to auth. The API answers 503 for
its own missing `ADMIN_TASKS_API_KEY` only: a 503 from anything inside the routes is answered
500, so `backend_key_missing` always means that key.

## Task pages

`/tasks` lists the registered tasks (title, version, whether it changes data,
resumable, needs a prior dry run, locks) with the latest run of each. The portal
imports only the task catalog, the spec and the signing helpers, never an
implementation or the runner, so it cannot run a task itself: it writes a signed
row into `tasks.runs` and the runner executes it only if the signature verifies.

| Route | What it does |
|---|---|
| `GET /tasks/<name>` | the parameter form, generated from the task's `Params` schema (text with length limit and pattern, numbers with a range, enums as selects, flags as checkboxes, lists of ids one per line with a maximum count); a type the form cannot express is not rendered and says so, and a required one removes the start buttons. Shows the last dry run |
| `POST /tasks/<name>/dry-run` | CSRF, audited, at most 10 per admin per 5 minutes; no step-up. A read-only task has a single "Run" button that uses this route |
| `POST /tasks/prepare` | the code step: verifies a fresh authenticator or recovery code (same lockouts as `/api/stepup`) and renders a confirmation page that holds a single-use token. It changes no task state |
| `POST /tasks/<name>/apply` | needs that token, bound to hash(task, version, canonical params hash, `dry_run=false`) |
| `POST /tasks/runs/<id>/cancel` | token bound to the run id; sets `cancel_requested_at` (the only column the admin role may update); idempotent; only for queued or running runs |
| `POST /tasks/runs/<id>/resume` | token bound to the run id and its params hash; a new signed request with `resumes_run_id` and the same params |
| `GET /tasks/runs`, `GET /tasks/runs/<id>` | history (filters `task`, `state`, `page`) and one run: state, progress, the typed result (rendered through the task's `Result` schema; integers, booleans and ids only), the runner's refusal code with an explanation, sanitised events (code, counters, ids; 50 per page) and whether a checkpoint exists |
| `GET /api/tasks/runs/<id>?after=<seq>` | JSON for polling: state, progress and the events after `seq` |

Everything works without JavaScript (the run page has a Refresh link). The run
page loads one self-hosted script, `/static/tasks.js`, that polls the JSON every
two seconds while the run is active, shows a "Live" indicator and reloads once
when the run ends; it writes with `textContent` only. The content security
policy stays `script-src 'self'`.

### Look and fonts

The portal follows the interface's design system (`DESIGN.md`): paper-mist ground,
white panels on hairlines, one blue, Instrument Sans for text and JetBrains Mono
for values (setting keys, ids, hashes, task parameters). The tokens are CSS custom
properties on `:root` in `static/admin.css`, named like the webapp's; dark mode
follows `prefers-color-scheme` from the same roles. The latin woff2 files live in
`static/fonts/` (OFL-1.1, notices in `static/fonts/LICENSE`) and are served by
`/static/fonts/<name>.woff2` with `font/woff2`, `nosniff` and a one-year immutable
cache, the only response the portal lets a browser keep. Nothing is loaded from
another origin, so the content security policy is unchanged.

Starting a real run inserts the run row (state `queued`, signed as `tasks/request`)
and the `task.run.requested` audit row in one transaction; a task that requires a
prior dry run is refused unless a succeeded dry run of the same task, version and
params hash finished less than 24 hours ago and before now (the runner checks again
against the signed request time, and the page shows the runner's refusal code
if it still refuses). Parameters travel only in POST bodies, never in a URL, and
the audit row carries the validated parameters through the usual masking. All
refusals are fixed sentences that never repeat a submitted value.

## Serialisation and the locks outsiders cannot take

Audit writes, settings writes, sign-ins and the setup token are serialised by row
locks on `admin.lock_rows` (`audit_chain`, `settings_writer`, `signin`, `setup_token`),
taken only through `admin.take_lock(name)` (SECURITY DEFINER; nobody else holds any
privilege on the table). Postgres advisory locks are not used for any of this, because
`pg_advisory_lock` is executable by every role and its keys live in one cluster-wide
namespace: any database login (the backend, the auth service, the user-code executor's
role) could take the repository's constant keys and stall the whole admin plane. Taking a
row lock gives up after 5 seconds with SQLSTATE `55P03`, so a stuck holder is a quick,
clear failure (the audited action fails closed) rather than a hang, and the integrity loop
raises `lock_blocked` for it. The lock order is always `settings_writer`, then
`audit_chain`.

## What each database role can and cannot do (summary)

| Role | Audit log | Settings store | Notes |
| --- | --- | --- | --- |
| `bc_admin` (portal, CLI) | `INSERT`, `SELECT`; may not write the runner's lifecycle actions (`task.run.started`, `task.run.finished`, `task.run.quarantined`, `settings.task_set`) | entries and manifest (signed rows only verify with the master key), history `INSERT`/prune, `history_wraps` `INSERT`; cannot move the keyset row to a new version, cannot change a history row | cannot read `app`, `auth`, `google`, `jobs` |
| `bc_tasks` (runner) | none: no read, no insert; rows only through `tasks.audit_append`, `tasks.begin_audit` and `settings.task_write_keyset` (definer functions owned by `bc_tasks_def`) | its own view; the keyset only through `settings.task_write_keyset`, for a `running` apply run of the matching `keyset.*` task whose start the function recorded, once per run | cannot insert runs |
| `bc_tasks_def` | NOLOGIN owner of the runner's functions; holds only what they touch | | nobody can connect as it |
| `bc_count_app`, `bc_count_auth`, `bc_count_google` | none | none | NOLOGIN owners of the count, revision and outbox functions; column `SELECT` on their own schema |
| `bc_tasks_purge_google` | none | none | NOLOGIN owner of `google.purge_unencrypted_credentials(apply)`; `DELETE` on `google.oauth_credentials` (and `SELECT` on `user_id`, `doc`), nothing else; `EXECUTE` for `bc_tasks_data_google` only |

What grants cannot close, and what detects it: the database cannot verify an HMAC.
A holder of both the portal's and the runner's database credentials (and no master key) can
still queue a row of its own and drive the runner's functions through it, but nothing it writes
verifies: the audit row carries a hash it cannot compute (`audit_chain_broken`), the keyset
row has no valid signature (`bad_signature`, and every reader refuses it). The portal's
credential alone can still mark a pending notification `sent` or `failed` (the sender uses
that same role); resetting, replaying or editing a delivered notice is refused. Whoever holds
the master key can sign anything: that is inherent to a shared key (see
[the threat model](#threat-model-notes)).

### Threat model notes

* A service's heartbeat (`settings.report_state`) is **advisory readiness information**,
  not proof. It is bounded (the reported revision is kept as reported so a rolled-back store shows, rejected names
  must be stored settings the caller's service reads, name lists are capped, at most 100
  instances a service), but a compromised service can still report a clean state for its own
  instances. The keyset gates therefore also require a fresh heartbeat (under two minutes) from
  every instance seen in the last 15 minutes and from each required service, they run again
  immediately before `keyset.drop_old` writes, and `drop_old` and `reencrypt` rely on a full
  scan of the data, not on the heartbeats, for the safety of the data itself. The one place a
  heartbeat narrows a scan is `drop_old` with `mongo_retired` (Postgres alone): it needs the
  operator's signed statement, the runner's write mode `postgres` for every group, and every live
  instance reporting `write_stores = postgres` (admin revision 0018; the older six-argument
  `report_state` still works and reports them as unknown, which refuses).
* A process that holds `SETTINGS_MASTER_KEY` can sign task requests and audit rows without any
  admin's authorisation; the signature proves that a holder of the key signed, not that an admin
  stepped up.

## Background loops

In full portal mode (never in the bare gate) the service runs three loops. Each is
one asyncio task guarded by a lease, a row in `admin.loop_leases` that the leader
renews on every pass: with several admin processes only one runs a given loop, the
others stand by and retry (the status says `standby`, with when it began), the lease is
released on shutdown and a crashed leader's runs out after two minutes. A lease is
used instead of an advisory lock because advisory locks are one namespace every
database login can use (the backend's role could have held the key and stopped the
loops); only the admin role can touch the lease table. Intervals are
jittered, a failing pass is logged by exception class only (never a message, address
or payload), counted, and retried with a growing delay (up to 8 times the interval);
nothing a loop does can stop the service. `ADMIN_LOOPS_ENABLED=false` switches them
off (the old plain cleanup of sessions and counters then runs instead).

| Loop | Every | What it does |
| --- | --- | --- |
| `notifications` | 15 s | mails every address in `PLATFORM_ADMIN_EMAILS` about pending rows of `admin.notifications` |
| `retention` | 1 h | removes old rows, see the table below |
| `integrity` | 10 min | runs the settings store check and reads the keys services reported as rejected |

**Mail.** The text is fixed per kind (`settings.changed`, `settings.keyset_changed`,
`settings.keyset_reencrypt`, `tasks.run`, `settings.integrity`) and names only the
action, the setting or task, the version or run id and the requesting admin. Values,
parameters, payload fields a template does not print and key material are never
read. A row of an unknown kind, or a payload that does not fit its template, is
marked `failed` (`unknown_kind` / `bad_payload`) and never rendered. A row becomes
`sent` only when every current admin's mail was accepted; admins already served are
remembered as truncated digests, so a retry mails only the rest. A failing delivery
is retried after 1, 2, 4 and 8 minutes and then marked `failed` (`delivery_failed`).
At most `ADMIN_NOTIFY_MAX_PER_MINUTE` mails (30) go out a minute. Each batch writes
one audit row `notifications.batch` (actor kind `system`, counts only). If mail is
not configured (`MAIL_SMTP_SERVER`, `MAIL_SENDER`) the loop idles, rows wait, and the
status says `mail not configured`.

**Retention.** Every statement is bounded (1000 rows) so a backlog drains over several
passes. The audit log and the settings entries, history and manifest are never
touched.

| Data | Removed |
| --- | --- |
| sessions | ended more than 7 days ago |
| sign-in challenges | expired more than 1 day ago |
| rate-limit counters and used step-up tokens (`admin.attempts`) | older than 48 hours |
| `tasks.run_events` | older than 90 days |
| `tasks.checkpoints` | of runs finished more than 30 days ago |
| `settings.service_state` | rows older than 7 days of a service with no newer row (a service that still reports prunes its own) |

The admin role holds DELETE on `tasks.run_events`, `tasks.checkpoints` and
`settings.service_state` for this; the runner role still can only append.

**Integrity.** Each pass runs the settings store check, verifies the next slice of the
audit chain (up to 5000 rows) from a checkpoint kept in `admin.audit_verify_state` (the last
verified `seq` and that row's hash; it only moves forward, and a break holds it in front of
the break so the alarm repeats every pass: `audit_chain_broken`, or `audit_checkpoint_bad` when
the checkpointed row is gone or changed), probes the two row locks the admin writes depend on
(`lock_blocked`) and reads the keys services reported as rejected (only names the registry
knows). Any problem (a bad signature, a missing row, a manifest mismatch, a broken audit
chain, a blocked lock, a version of a secret that no sealed copy opens, a key a
service rejected) sets the integrity status and is mailed once per incident: the
same set of problems is not mailed again within 24 hours (kept in memory and, after a
restart, found through the outbox row's dedupe key). When the problems are gone the
status is ok again, and a later recurrence is a new incident.

**Seeing the status.** `Portal.loop_status()` returns each loop's last run, last
outcome (a short fixed phrase with counts), consecutive failures and whether this
process leads it; `Portal.integrity_status()` returns `ok` (None until the first
check), `(setting, reason)` pairs and the time of the check; `Portal.mail_status()` is
`ok` or `mail not configured`. All are in-memory copies of one shared holder
(`backend/admin/loops/status.py`) for the Health page and the shell banner.

| Variable | Default | Meaning |
| --- | --- | --- |
| `ADMIN_LOOPS_ENABLED` | `true` | run the loops |
| `ADMIN_NOTIFY_INTERVAL_SECONDS` | `15` | outbox pass interval |
| `ADMIN_NOTIFY_MAX_PER_MINUTE` | `30` | mail rate limit |
| `ADMIN_RETENTION_INTERVAL_SECONDS` | `3600` | retention interval |
| `ADMIN_INTEGRITY_INTERVAL_SECONDS` | `600` | integrity check interval |
