# Internal admin service

A small separate service, started from the backend image with
`python -m backend.admin.serve`. It is not part of the public API: it has its
own application, no CORS, and shares no router or container with the backend.

## Enabling the portal

The service always starts, but the sign-in portal runs only when all of these
are set; otherwise it is the bare gate (`/healthz` and 404s) and logs one
warning naming what is missing.

1. `PLATFORM_ADMIN_EMAILS` **(required, set by you)** in the root `.env`: the
   super admin list, comma-separated. Only these addresses can sign in.
   `deploy.sh` never writes it and prints a notice while it is unset.
2. `SETTINGS_MASTER_KEY` and `BC_ADMIN_PASSWORD`: generated by `deploy.sh`
   into the root `.env` on first run, never overwritten. Back up the master
   key; it cannot be recovered. `BC_ADMIN_PASSWORD` and `BC_ADMIN_MIG_PASSWORD`
   go unencoded into database URLs, so they may use only letters, digits, `.`,
   `_`, `~` and `-`; `deploy.sh` and `postgres/ensure-admin-roles.sh` refuse
   anything else (generated values are hex).
3. Sign-in codes are mailed, so set `MAIL_SMTP_SERVER`, `MAIL_SENDER` (and
   `MAIL_USER` / `MAIL_PASSWORD` if needed) in the root `.env`. Compose reads
   them from there for this service, which has no `env_file`.

The three portal settings default to empty in the compose file instead of
being marked required: `docker compose config` and existing deployments keep
working, and an upgrade that has not set the admin list starts in the bare-gate
mode instead of failing.

## Network

- Published on the host's loopback only (`127.0.0.1:${ADMIN_PORT:-8100}`) and
  never referenced by nginx. Reach it from elsewhere with an SSH tunnel:
  `ssh -L 8100:127.0.0.1:8100 <host>`, then open `http://localhost:8100`.
- Two networks, and not `default`:
  - `admin-edge` (`ADMIN_EDGE_SUBNET`, default `172.30.77.0/29`), with only
    the admin service on it, carries the published port. Docker's port
    publishing makes host traffic arrive from that network's gateway
    (`ADMIN_EDGE_GATEWAY`), which is allowed in addition to `ADMIN_ALLOWED_IPS`.
  - `admin-db` is `internal` (no gateway, no route out) and shared only by the
    admin service and `app-postgres`. The service connects as the `bc_admin`
    role, which can use schema `admin` only.
- **What `ADMIN_ALLOWED_IPS` does and does not protect.** In this layout every
  connection from the host reaches the service as the `admin-edge` gateway
  (`ADMIN_EDGE_GATEWAY`), which is always allowed, so the service cannot tell one
  client from another. `ADMIN_ALLOWED_IPS` therefore restricts nothing that
  arrives through the published port: it only matters when clients reach the
  service with their own address (a different network layout, or real proxies
  listed in `ADMIN_TRUSTED_PROXIES` that report it in `X-Forwarded-For`). The real
  boundary is the host port binding (`127.0.0.1` only) and who can log in to the
  host: any local process, and any reverse proxy running on the host, passes the
  address gate. **Never put a proxy in front of port 8100** and never publish it
  on another interface. Consequences: session address binding, the "new address"
  notice and the address in audit rows show the gateway for everyone; the per-address
  limits cannot separate clients, so the pre-sign-in limits also use the (email)
  and (challenge) dimensions instead of one global address bucket (see "Sign-in
  and sessions"). At start the service logs a WARNING when the gateway is set and
  `ADMIN_TRUSTED_PROXIES` is empty, because that is this situation.
  If a proxy is unavoidable, set `ADMIN_TRUSTED_PROXIES`, `ADMIN_ALLOWED_IPS` and
  `ADMIN_ALLOWED_HOSTS` / `ADMIN_PUBLIC_ORIGINS` for it; `deploy.sh` prints a reminder when
  any of those is set in the root `.env`. An SSH tunnel is the supported way in.
- **Cookies and ports.** The `__Host-` cookies carry no port, so a browser sends
  `__Host-bcadmin` to every service on the same host name, whatever the port
  (`localhost:3000`, another tunnel, a second environment's portal tunnelled to
  another port). `SameSite=Strict` does not help (same site), though `Origin` and
  `Sec-Fetch-Site` are still checked. Use a host name of your own that resolves to
  loopback for each environment (for example `admin.localhost` in the `/etc/hosts`
  of the machine that opens the tunnel, added to `ADMIN_ALLOWED_HOSTS` and
  `ADMIN_PUBLIC_ORIGINS`), which gives each portal its own cookie jar, and do not
  run untrusted software on a machine that holds a tunnel.
- Because the service is not on `default`, no other container can resolve or
  route to it. Attaching it to `default` as well would let Docker pick which
  network host traffic comes from; keep the layout as it is.
- Compose 2.24 with Docker Engine 27 sometimes attached a container on two
  networks (`app-postgres`, `admin`) to only one of them when the networks were
  created in parallel (3 to 5 of 10 up/down runs). The compose file therefore
  gives those services explicit network `priority` values; with them, 0 of 40
  plain `docker compose up` runs lost a network. Setting
  `COMPOSE_PARALLEL_LIMIT=1` in the root `.env` does not help in this Compose
  version (5 of 10 runs still lost a network), so it is not relied on;
  `deploy.sh` and the check script still export it as an extra precaution (this
  also serialises `pull` and `up --build`, so deploys can be slower). A
  service that logs a name-resolution failure for `app-postgres` has hit this:
  `docker compose up -d --force-recreate app-postgres admin`.
- `scripts/admin-compose-check.sh` verifies all of this with real containers
  (see below).

## Acceptance check

`scripts/admin-compose-check.sh` needs docker (compose v2), curl and openssl. It
builds the backend image from the checkout unless `ADMIN_CHECK_IMAGE` names
one, then starts its own throw-away compose project on a random free loopback
port and an unused subnet, with new secrets, and removes everything on exit
(`KEEP=1` leaves it up). It checks, against the running containers: the
host reaches `/healthz` and the sign-in page through the real gateway address;
the LAN address is refused; a container on the default network cannot reach
the service; the health check is healthy in bare-gate mode and with a database,
master key and admin list; `docker compose config` parses with and without the
optional variables; the container is read-only, non-root and capability-free;
and `bc_admin` can read only its own schema and cannot update the audit log. It
also checks the deployment around the service: a `.env` holding only what
`deploy.sh` generates plus the operator's values renders; only the intended
services publish a port (Temporal and the databases publish none); the master
key reaches the store readers, the admin service and the task runner and never
the Temporal worker; DEBUG and API_DOCS_ENABLED are not pinned; the Temporal and
Umami databases take the generated password; and the host commands work through
compose (`bootstrap-keys` prints no key material and is refused the second time,
the import dry run and the drift check read the compose configuration from
standard input, and the one-off container has none of the stack's keys in its
environment). It also renders the compose file next to a `.env.deployment` filled
with dummy Stripe, Google, mail, Mongo and key values and asserts that none reaches
a service outside the four store readers (and that the worker's whole environment is
its handful of variables), checks with real containers that the Mongo seed leaves no
`seeduser`, and that the nginx rules for Umami pass only the tracker.

## Gate

Every request must pass, in order: the `Host` allowlist, then the client
address allowlist. A request that fails either gets a bare 404 and a rate
limited warning log line. Routes are registered with a required level;
anything unregistered is a 404. `/healthz` answers `ok` to loopback peers and, for host-side monitoring, the admin network gateway.
Responses carry a strict CSP and related security headers, a `Permissions-Policy`
that turns every powerful browser feature off, and, when the request arrived over
TLS (the ASGI scheme, or `X-Forwarded-Proto: https` from a trusted proxy only),
`Strict-Transport-Security` (one year, subdomains). Bodies are capped
at 64 KB and only form or JSON content types are accepted.

## Sign-in and sessions

Sign-in is by an 8-digit code mailed to an address listed in
`PLATFORM_ADMIN_EMAILS` (read once at start). The sign-in form
answers every address the same way, so it does not reveal who is an
admin. A code lasts 10 minutes, works once and allows five attempts; asking
for a new one cancels the old one. Many wrong codes across the service pause
sign-in for 10 minutes; admins are mailed once when that happens. The
sign-in mail uses the platform's `MAIL_*` settings.

Who can be locked out by what. Anyone who can reach the sign-in page can ask for
a code for a listed address and type wrong ones, so wrong **email codes** never
lock the address itself:

- they count against the pair (email, client address): five wrong codes lock that
  pair for 15 minutes, then 1 hour, then 4 hours, and the genuine admin can still
  sign in from another address with a valid code. Behind the shared gateway address
  (see "Network") the pair is everyone, so there no pair lock is applied and only
  the per-challenge limit (five attempts, then the challenge is burned) and the
  request limits below hold;
- a ceiling of 30 wrong email codes per address and hour, from any addresses, is
  an alert (an audit row `signin.failure_surge` and one mail to every admin), never
  a lock;
- code requests are limited per (email, address) (3 per 10 minutes), per address
  (10 per 10 minutes; one high flood cap for the shared gateway address) and, at a
  higher ceiling, per email (12 per 10 minutes), so one client cannot use up the
  admin's requests from another;
- the lockout mail goes out at most once per address and hour;
- the **second factor** keeps its own lock per admin email (five wrong codes in five
  minutes, escalating as above): it is reached only with a valid email code, so
  only someone who already passed the first step can feed it. Operator `unlock`
  clears that lock and the factor counters; a pair lock lapses by itself.

What brute force costs: with the limits above one address gets at most 15
guesses per 10 minutes at an 8-digit code, so a guessing run is not practical, and
a flood of wrong posts against one challenge cookie costs memory only: after a few
posts (the five counted attempts and a little slack) the service answers from memory
with no database work and no audit row, and a refused challenge writes one audit row
in total. The residual: an attacker at the same shared address as the admin can
keep requesting codes (each new request cancels the previous code), which is a
nuisance, not a bypass; the host boundary is what keeps them out.

A session cookie (`__Host-bcadmin`, `Secure`, `HttpOnly`, `SameSite=Strict`) holds
a random token; only its hash is stored. Sessions end after 30 minutes idle or
8 hours in total (`ADMIN_SESSION_IDLE_MINUTES`, `ADMIN_SESSION_ABSOLUTE_HOURS`
can only shorten these), are bound to the client address and browser, and at
most three stay live per admin. A signed-in session whose second factor is still
pending can reach only `/mfa/enrol*` (no factor yet), `/mfa/verify` (factor set up)
and `/logout`. Removing an address from
`PLATFORM_ADMIN_EMAILS` ends its sessions at the next start or request.
Every state-changing request needs a CSRF token and a same-origin
`Origin` (`ADMIN_PUBLIC_ORIGINS`). The session's token is derived from its id
and its current token hash, so it changes whenever the session token rotates.
The sign-in forms, shown before a session exists, use a signed double-submit
cookie; cookies do not separate ports on `localhost`, so another local service
could plant that cookie, and what actually protects those forms is the `Origin`
(scheme, host and port) and `Sec-Fetch-Site` check, which every state-changing
request must pass. Operator commands:
`python -m backend.admin unlock <email>`, `resume-sign-in`, `revoke-sessions [email]`.

## Second factor, recovery codes and step-up

Every admin needs an authenticator app (TOTP, 6 digits, 30 s). The first
sign-in leads to `/mfa/enrol`: scan the QR code (drawn by the service, nothing
is fetched) or type the key, confirm with one code, and ten single-use recovery
codes are shown once. The secret is stored encrypted, bound to its row and the
address. A code works once (a replayed or concurrent duplicate is refused), one
step of clock drift either way is tolerated, and five wrong codes in five
minutes (or fifteen in a day) lock the address with the same escalation as above.
Guesses are reserved before a code is checked, so at most five are evaluated per
five minutes however many requests arrive at once.
A recovery code can be used instead of an authenticator code; every admin is
mailed when one is used, when an address is locked, when a factor is set up,
and when an admin signs in from an address not seen in their recent sessions.

Sensitive actions that keep an account recoverable (making new recovery codes,
adding or replacing the authenticator) need a fresh code **sent with that
request**: the 300 seconds that sign-in itself opens do not count, so a stolen
session cookie alone cannot do them. Making new recovery codes also mails every
admin. Ending another admin's session needs a fresh code within
`ADMIN_STEPUP_SECONDS` (default 300, at most 600); the portal asks for it on a
prompt page. Actions that
must not ride on that window use a single-use token (120 s) bound to the exact
action, from `POST /api/stepup`.

If the authenticator and the recovery codes are both lost, only the operator on
the host can reset the factor (there is no reset by another admin, and none by
email). The reset is audited, revokes the admin's sessions, mails every admin and
makes the next sign-in enrol again:
`python -m backend.admin reset-factor --email <address> --yes`. On a
single-admin installation this command is the only way back in.

Without `ADMIN_DATABASE_URL`, `SETTINGS_MASTER_KEY` and `PLATFORM_ADMIN_EMAILS`
the service starts as the bare gate: `/healthz` and 404s only, with one warning
naming the missing settings (never their values); see "Enabling the portal"
above for how the compose service receives them. Settings that are present
but invalid stop startup.

## Portal pages (read-only)

After the second factor the portal shows a shell (navigation, the signed-in
address, sign out, a notice area) and these pages. Every one is a `GET` at the
`SECOND_FACTOR` level; none changes state. `Settings` is listed in the navigation as not
available yet; the task pages are described under "Task pages" below.

| Page | What it shows |
|---|---|
| `/` | Cards linking to the pages below |
| `/health` | Service heartbeats from `settings.service_state` (names and numbers; no report for 120 s is "stopped"), database reachability, the admin schema's Alembic state (current against the expected head) and the `app`, `auth` and `google` schemas' revisions where this role can read them (otherwise "not available to this role": the role has no access to those schemas on purpose) |
| `/config` | The settings registry joined with the store and the env-override names services report: section, readers, type, reload class, tier, source (store, environment, default), version, last change. Secrets show only "set" or "not set" and the last change, never a value, length, prefix or hash (the query never selects them). `NEXT_PUBLIC_*` keys are "build argument", tier T5 keys "environment only" with no values. Filters `section` and `tier` are validated allowlists (400 otherwise). Also lists the super admins from `PLATFORM_ADMIN_EMAILS` |
| `/metrics` | Platform counts (organisations, users, forms, responses, 12 weekly buckets). Counts only, read from Postgres through `admin.platform_counts()` |
| `/audit`, `GET /api/audit` | Newest first, keyset pagination (`before` is a `seq`), filters `actor`, `action` (exact or dot-separated prefix), `outcome`, `from`, `to` (a date or an ISO time; `to` as a date includes that day), `limit` up to 200; all validated (400 otherwise). Payloads are shown masked and escaped. The page shows the chain head and points to `python -m backend.admin audit-verify`; the chain is not verified inside a request. No export |
| `/sessions` | Your live sessions (created, last seen, address, a short fingerprint of the browser identification) with the current one marked; revoke forms post, with the CSRF token, to the existing account routes |

A notice area at the top of every page carries a permanent reminder to back up
`SETTINGS_MASTER_KEY` (it cannot be recovered) and, when a service reports a
pending restart, a restart notice.

`admin.platform_counts()` is created by `postgres/ensure-admin-roles.sh`, not by
an Alembic revision: the admin roles cannot read the `app` and `auth` schemas
and the migration role owns nothing there, so the function is a SECURITY DEFINER
owned by a dedicated role, `bc_admin_counts` (NOLOGIN, no superuser, no create
rights anywhere, owns no objects). That role has `USAGE` on `app` and `auth` and
column-level `SELECT` on only the columns the function reads; the script
re-applies those grants on every deploy, so they appear once the application
migrations have created the tables. The function takes no arguments, writes
nothing, calls only `pg_catalog` functions (never an object another service's
role owns, so those roles cannot make it run their code), pins `search_path`,
and is executable by `bc_admin` alone. The counts follow the Postgres store, so they are complete
once the application serves from Postgres; before the application migrations
have run the page says they are not available.

## Settings pages (changing settings)

`/settings` lists every setting (filter by section or tier); `/settings/<key>`
shows one with a typed form, `/settings/<key>/history` its versions,
`/settings/integrity` runs the store verification on demand and
`/settings/notifications` lists the queued admin notices (read-only; the
sender is separate). All use the `SettingsService`, so validation, tiers,
versions, history, audit rows and notices are the service's.

Changing a setting takes two steps because the pages use no script:

1. The edit, clear, restore or purge form includes a fresh authenticator or
   recovery code and posts to `/settings/<key>/prepare`. That is the only
   mutating settings route without a token; it writes nothing. It validates the
   value, checks the typed confirmation (tier T3), checks the code, and answers
   with an "apply" page holding a single-use token.
2. The apply page posts to `/settings/<key>/set`, `/clear`, `/restore` or
   `/purge-history`. Those routes require a token issued for exactly that
   action, key, new value and the version the admin saw (the service's keyed
   action hash), so a token cannot be replayed or moved to another change. A
   change made by someone else in between is refused as stale.

A new value is carried between the steps only as an AES-256-GCM blob bound to
the session, action, key and version, valid for two minutes, so a secret never
appears in HTML, a URL, a log line or an audit row. Secrets are written
through a write-only password field and never prefilled; history shows only
"set" or "cleared" for them (the last five sealed versions are kept; "purge"
deletes the older ones). Key material (T4) shows no form, since a maintenance
task rotates it, and environment-only keys (T5) can only be read. The portal
asks for the code on every change, including tier T1 (the service itself only
requires it from T2).

Redirect messages use a fixed list of codes (`?notice=...`), never values.
`/settings/integrity/run` needs no step-up (it reads only), is limited to three
runs a minute and shows setting names with reason codes; a failed last run
adds a notice to every page.

## Settings store: what the database guards do and do not do

Schema `settings` holds signed (and, for secrets, encrypted) rows, a signed
manifest and per-service views. The triggers on its tables stop mistakes and a
compromised runtime role (no deleting entries, versions and the manifest
revision only go up by one, no future history rows). They do not stop the
migration role, which can disable triggers. Tampering is detected instead:
every row carries a signature, the manifest signs the full set of keys, versions
and readers, and every change is in the audit trail; `settings-verify` checks
all three against each other, including a wiped or rolled-back store.

Each reader's manifest view lists every key, version and reader set, not only
the rows that service may read: a service needs that to notice a row withheld
from it. Key names are therefore visible to every reading service; values never
are.

A change to a step-up setting must carry the setting's current version in the
step-up (`SettingsService.action_hash(action, key, value, expected_version)`).
The portal reads the version when it renders the form, binds it into the hash it
asks the step-up module to issue a token for, and passes the same
`expected_version` to the service, which checks it inside the write transaction.
A replayed token, or a form left open while someone else changed the setting,
fails with `stale_version`.

### Key material is checked when it is written

The registry names a format for the keys that are key material, and every write
(`settings-set`, `settings-import`, `bootstrap-keys`, the portal) refuses a value
that does not meet it, with a refusal code and a sentence that never shows the value:

| Key | Format | Refusal codes |
|---|---|---|
| `AUTH_JWT_SECRET`, `AUTH_INTERNAL_NOTIFY_KEY`, `TEMPORAL_API_KEY` | at least 32 characters, not a known placeholder, not a repeating or low-entropy pattern (`openssl rand -hex 32` is what the deploy scripts make) | `too_short`, `low_entropy`, `weak_secret` |
| `AUTH_AES_HEX_KEY` | a Fernet key (32 bytes, url-safe base64) of bytes that are not all alike | `weak_secret` (not Fernet), `low_entropy` |
| `MASTER_ENCRYPTION_KEYSET` | a Tink keyset Tink can build an AEAD from: key ids once each, an enabled primary key | `bad_keyset` |
| `CUSTOM_DOMAIN_ASSERTION_KEYS` | `id:secret` pairs, secrets of 16+ characters | `bad_pairs` |
| `CUSTOM_DOMAIN_WEBHOOK_SECRETS` | one or two secrets of 16+ characters | `bad_list` |

Published values are refused as before (`weak_secret`). The master key
(`SETTINGS_MASTER_KEY`) must also decode to 32+ bytes that are not nearly identical.
An upgrade imports what the old `.env` holds: a legacy short or low-entropy
`AUTH_JWT_SECRET` is now **refused with `too_short` or `low_entropy`** instead of being
moved into the hardened store; replace it (everyone is signed out once) and import
again. The services that only read the store do not apply these checks, so a value
stored earlier never stops one from starting. The keyset a stack published long ago
is still accepted (its responses could not be read with another), with the existing
warning.

### Rollback and wipe protection

The signed rows and manifest cannot be forged without the master key, but an older
validly signed state can be put back, and a database can be replaced by an empty one.
What stops that, and what does not:

- Each service keeps the highest manifest revision and row versions it accepted in
  its signed snapshot (`SETTINGS_SNAPSHOT_DIR`, a volume in the compose file). With
  `SETTINGS_STORE=required` a service **refuses to start** on a store whose revision
  is below that floor (`StoreError`: "settings store is behind this service's
  record"), and on a never-written store (revision 0) while its environment lacks a
  key it cannot run without (`AUTH_JWT_SECRET`, `AUTH_AES_HEX_KEY`): a wiped database
  looks like that. After a restore or replacement you meant to do, remove the snapshot
  directory (or the volume) and restart.
- The floor is the highest revision the service reports in `report_state`
  (`revision_applied`), and the **admin integrity check** compares it with the store:
  a manifest revision below what a live service (reported within the hour) accepted is
  `store_behind_services` on the health page and in the integrity mail, whatever the
  database's own audit trail says (a full restore brings back an older audit trail
  too, but not the running services' memory). `settings-verify` also reports
  `manifest_rollback` against the audit trail.
- Not covered: a validly signed older state on a service that starts with **no**
  snapshot (a recreated container with its volume gone, `docker compose down -v`,
  a first start) is accepted. Nothing outside the container and the database holds
  a floor for it, and an attacker who can write the database (or restore a backup)
  and also replace the service's volume could use that. The integrity check above
  is the compensating alarm; for the strongest guarantee keep the snapshot volumes
  and back them up with the master key. A wiped store on a stack that still keeps
  its secrets in the environment (not yet migrated) is indistinguishable from an
  unmigrated one, so non-secret settings (trusted proxies, SSO, webhook URLs) fall
  back to their code defaults there until the floor exists.

### The actions executor and key material

`temporal/actions-executor` runs form-creator code with `exec`, a stripped globals
dictionary and `__builtins__` set to `None`. That is not a sandbox: a known
introspection chain reaches `os.environ` from such code. The registry therefore
lists the executor as a reader of **no** key material, and its environment must hold
as little as possible: not `SETTINGS_MASTER_KEY`, not `DATABASE_URL`s of other
services, and, in time, neither `AES_HEX_KEY` nor `API_KEY` (today the executor's own
code still reads them, to decrypt action secrets and to call the backend's job
routes, so an executor that is given them exposes them to action authors; moving
decryption and the callback behind a per-run credential from the backend is the open
change). The repository's compose files do not run the executor (the deployment
workflow deploys it separately), so its environment is whatever that stack passes:
check it against `temporal/actions-executor/.env.example`.

## Host commands for the settings store

`python -m backend.admin <command>` runs on the host (in a one-off container that
has `ADMIN_DATABASE_URL` and `SETTINGS_MASTER_KEY`). The operator holds the master
key and the database role, so these commands need no second factor; every change
is an audit row with actor kind `cli`, written in the same transaction. The
commands print counts, setting names and short reason codes, never a value.

| Command | What it does |
|---|---|
| `bootstrap-keys [--export-worker FILE] [--existing-stack] [--fill-missing]` | Fresh install: generates `AUTH_JWT_SECRET`, `AUTH_AES_HEX_KEY`, `AUTH_INTERNAL_NOTIFY_KEY`, `TEMPORAL_API_KEY` and the response keyset straight into the store, prints only the keyset's key-id fingerprint (the value services report as their keyset fingerprint) and the master-key fingerprint. Refused whatever the flags when the stack holds data (users or responses in `admin.platform_counts()`, plus, **only when `MONGO_URI` is in the command's own environment**, a non-empty `users` or `form_responses` collection in that Mongo server; `deploy.sh`'s one-off container has no Mongo credentials, so `deploy.sh` decides the Mongo half itself, see below) or when that cannot be established (fail closed): a new keyset could not read what the old one encrypted, so an existing stack imports its keys with `settings-import` instead. Also refused when `--existing-stack` is passed, when the environment already carries one of the keys (import instead), or when the store holds one (`--fill-missing` finishes an interrupted run and adds only the missing ones). `--export-worker FILE` writes `API_KEY` and `AES_HEX_KEY`, the two copies the Temporal worker keeps (it never gets the master key), to a new private file or appends them to a private env file that has neither; `--export-worker-only` skips generation. |
| `settings-import --from-compose-config [--dry-run] [--prefer SERVICE]` | Reads `docker compose config --format json` on standard input (never written to disk) and imports each setting once, from the services that read it (`backend`, `jobs-worker`, `auth`, `integrations-googleform`, `admin`). Prints `would_import`, `already_in_store`, `empty`, `unknown`, `env_only`, `conflict` and `refused <key> <reason>` as counts and names. Services that disagree on a value are imported neither way until `--prefer SERVICE` picks one. Never overwrites. `--env-file PATH` (without the other options) is the older single-file import. |
| `settings-drift [--from-compose-config \| --env-file PATH]` | Compares the same sources with the store: `equal`, `differs <key> <service>`, `env_only`, `store_only`. The workers' `API_KEY` and `AES_HEX_KEY` are compared with `TEMPORAL_API_KEY` and `AUTH_AES_HEX_KEY`. `MASTER_ENCRYPTION_KEYSET` counts as `differs` when the stored keyset lacks any key id of the environment's (ids compared, never values). Exit 1 when any value differs. |
| `settings-prune --env-file PATH ... [--apply] [--swap] [--keep NAME]` | In 4.0 an environment value wins over the store, so a stale value left in `.env` silently overrides a portal change. Prune removes the settings the store already holds with the same value (comments and everything else stay). Without `--apply` it only reports. With `--apply` it writes `PATH.pruned` and a private backup `PATH.pre-v4.<time>` (both mode 600, never over an existing file); `--swap` then replaces the original with the pruned copy. A key whose value differs is never removed (exit 1: fix it first). Backups hold the old secrets: delete them when the stack runs well. Use `--keep` for a name something outside the store still reads (the Typeform service keeps `AUTH_JWT_SECRET`, `AUTH_AES_HEX_KEY` and `MASTER_ENCRYPTION_KEYSET` in its environment). |
| `settings-env-export --keys A,B --out FILE` | Break-glass: writes the named settings, with values, to a new file (mode 600, refuses to overwrite). Audited by names. Delete the file when the incident is over. |
| `settings-set KEY (--stdin \| --value V) [--confirm KEY] --yes` | Sets a setting of tier T1 to T3 from the host. A secret is read from standard input, never from an argument. A T3 setting needs `--confirm KEY` (the typed confirmation). Key material (T4) is managed by tasks and environment-only settings (T5) are refused. |
| `settings-restore KEY --version N [--confirm KEY] --yes`, `settings-history KEY` | Restores a kept version as a new version; lists the versions (no values). |
| `settings-mail-apply --env-file PATH --test-to ADDRESS` | Saves the admin sign-in mail settings (`ADMIN_MAIL_*`, section `admin_mail`) from an env file. A test mail with a random code goes to ADDRESS with the candidate settings (the stored ones overlaid with the file); the operator types the code from the mail; only then are the keys saved. See below. |
| `setup-token [--new]` | Prints a one-time first-run setup token on the console only (refused when standard output is not a terminal unless `--allow-non-tty`). 160 bits, valid 60 minutes, one use; only a keyed hash is stored (the token is in no log and no audit row). A second call refuses while a token is active (it cannot be shown again): `--new` replaces it. Once any admin has a confirmed second factor the setup is closed and the command refuses; `reset-factor` is the only way back. |
| `master-key-fingerprint` | A short non-reversible id of the master key (`abcd-ef01-2345`), computed offline. `settings-verify` and `bootstrap-keys` print it too. Write it down with the key backup: a restored key with another fingerprint is the wrong key. |

**Admin sign-in mail.** The code that signs an admin in arrives by mail, so a
mail setting that cannot deliver locks every admin out. The `admin_mail` section
(`ADMIN_MAIL_USER`, `_PASSWORD`, `_SMTP_SERVER`, `_SMTP_PORT`, `_SENDER`,
`_STARTTLS`, `_SSL_TLS`, `_USE_CREDENTIALS`, `_VALIDATE_CERTS`; tier T3, read by
the admin service only, never the public `mail` section) therefore cannot be
saved by `SettingsService.set` or `import_once` unless the caller passes
`mail_verified=True`, its statement that a test mail was delivered with exactly
these settings. `settings-mail-apply` does that after the code round trip;
`settings-set` and `settings-import` cannot. Clearing and restoring an earlier
(already tested) version stay possible. An environment value still wins over the
store, which keeps `ADMIN_MAIL_*` in `.env` as the break-glass. The portal reading
these keys, and its own test-and-confirm flow, are the setup wizard below.

The setup token lives in `admin.setup_tokens` (migration `0011_setup_tokens`: one
active token at a time, 20 wrong tries lock it). `services/setup_token.py` has the
primitives the wizard uses (`issue`, `redeem`, `active`).

## First-run setup wizard

A fresh install has no way to sign in yet (codes are mailed, mail is not set up).
The wizard closes that gap without opening a door: it exists only while no admin
has a confirmed second factor **and** a valid setup token waits. Its pages sit
behind the same Host and address gate as everything else, and every refusal is the
bare 404 of an unknown path.

1. On the host, print a token (once, on the console; it is in no log):
   `python -m backend.admin setup-token` (`--new` replaces an unused one). It is
   160 random bits, valid 60 minutes, usable once.
2. Open `/setup` (through the SSH tunnel) and enter the token and one address from
   `PLATFORM_ADMIN_EMAILS`. The token travels in the POST body only, never in a URL.
   Wrong tries count against the token only within limits (5 per client and 15
   minutes, 8 per address and hour); past them a wrong try is refused without being
   counted or audited and the right token still works, so a flood from the one
   address everything shares cannot burn the token. 20 counted wrong tries lock the
   token for good (every admin is mailed, if mail works); `setup-token --new`
   replaces a locked or lost one. A wrong token, an unlisted address, an
   expired or locked token, a finished setup and a rate limit all get the same
   answer (a redirect back to `/setup`, which is the bare 404 when setup is closed)
   and the same database work. A right token creates a
   `setup` session: 60 minutes, 15 idle, bound to address and browser, able to
   reach second-factor enrolment and sign-out only. Every admin is told it started.
3. Enrol an authenticator on the portal's own enrolment pages and save the ten
   recovery codes. The first confirmed factor ends the token's life: `/setup`
   disappears and `setup-token` refuses (`reset-factor` is the only way back). The
   session becomes a normal signed-in one.
4. **Mail** (optional, `/setup/mail`): enter the server settings. A test mail with a
   six-digit code goes to your own address using exactly those settings; the
   `admin_mail` keys are saved (through the settings store, audited, with the
   delivered-test guard) only after you type the code. Saving needs a fresh
   authenticator code. Defaults are STARTTLS on port 587; STARTTLS and TLS from the
   start are never both on (refused by the server too), and implicit TLS needs its
   port stated. A saved password is never sent to a different server, and never over weaker
   transport than it was saved with: if the server, port or user name changed, or
   STARTTLS / TLS / certificate checking changed to something other than "protected
   and verified" (or to something different from an insecure setting it was already
   saved with), the password must be typed again. The environment (`ADMIN_MAIL_*`, then `MAIL_*`) wins over
   saved settings; the service reloads saved ones at most once a minute. You can
   skip the step and run `settings-mail-apply` on the host later.
5. **Finish** (`/setup/finish`): the master key fingerprint and a backup reminder
   (there is no escrow: nothing here stores the key). Tick the box and the wizard
   is closed in the database for good and every admin is mailed.

Steps 4 and 5 are reachable only by the admin who used the token, until they finish
or two hours after the token was used. After that every `/setup` path answers 404.
They are not reachable "before any factor exists": the second factor comes first, so
that nothing is saved without one.

Every step is audited (`setup.token_redeemed`, `setup.token_refused`,
`setup.token_locked`, `setup.mail_test`, `setup.mail_saved`, `setup.mail_skipped`,
`setup.completed`, plus the session, factor and settings rows of the existing
machinery); none holds a token, a code or a password. State lives in
`admin.setup_state` (migration `0012_setup_state`, which also allows the `setup`
session state). A lost token: `setup-token --new` before the first enrolment. The
wizard adds no write path of its own to the settings store.

## Deploying with `deploy.sh`

What you provide, and what `deploy.sh` generates (once; a value already present is never changed):

| | Where | Who |
|---|---|---|
| `PLATFORM_ADMIN_EMAILS` | root `.env` | you (required to enable the portal) |
| `ADMIN_ALLOWED_IPS` | root `.env` | you, only when you reach the portal from another address than the host (default `127.0.0.1/32`) |
| `SETTINGS_MASTER_KEY` | root `.env` | generated; **you back it up** (its fingerprint is printed at the end of a new install) |
| `DATABASE_URL` | not set in the bundled stack | compose builds each service's URL with its own database role; pointing the stack at an external Postgres is not covered by this compose file |
| database role passwords, `UMAMI_APP_SECRET`, `BC_TEMPORAL_DB_PASSWORD`, `BC_UMAMI_DB_PASSWORD`, `BC_MONGO_ROOT_PASSWORD` | root `.env` | generated (the last three for new volumes only) |
| `API_KEY`, `AES_HEX_KEY` | root `.env` | generated into the store, copied here for the Temporal worker only |
| `AUTH_JWT_SECRET`, `AUTH_AES_HEX_KEY`, `AUTH_INTERNAL_NOTIFY_KEY`, `TEMPORAL_API_KEY`, `MASTER_ENCRYPTION_KEYSET` | the settings store | generated by `bootstrap-keys` (nothing printed); imported on an upgrade |

So a bundled install needs one value from you, `PLATFORM_ADMIN_EMAILS`, plus `ADMIN_ALLOWED_IPS` in the cases above; the master key is the one value you keep safe.

**New install.** `deploy.sh` generates the secrets above, starts the database, creates the roles and applies every migration (including the `settings` schema), then runs `bootstrap-keys` in a one-off container before any service starts: the keys go into the store as the `cli` actor, only the fingerprint is printed, and the two worker copies are written to `.env` (mode 600, never printed). Then the services start. Last it shows a one-time setup token on the console only (`./deploy.sh setup-token --new` shows another while setup is not finished; it needs a terminal). The token is in no container log: the one-off container is removed when the command ends.

**A database that already holds data is never bootstrapped.** The two stores are checked in two places. The Postgres side (users, responses) is counted by `bootstrap-keys` itself. The Mongo side is **not** counted by `bootstrap-keys` in a `deploy.sh` run (its one-off container holds the admin database role and nothing else, never the Mongo root credentials, so the command's own Mongo check does not run there); `deploy.sh` decides it explicitly instead: a Mongo volume of this stack (found under the project name compose uses: the shell's or the root `.env`'s `COMPOSE_PROJECT_NAME`, else the directory name) or a `MONGO_URI` in `.env` or `.env.deployment` (an external Mongo it cannot look into) means the stack may hold data, and it never generates keys. In every such case `deploy.sh` stops before any service starts, stores no keys and says so: a new keyset could not read what the old one encrypted. Put the keys the stack has used in `.env` (`AUTH_JWT_SECRET`, `AUTH_AES_HEX_KEY`, `MASTER_ENCRYPTION_KEYSET`) and run `./deploy.sh` again; it imports them (see `settings-import`). Volumes found under a project name other than the one compose will use (say `COMPOSE_PROJECT_NAME` added to `.env` after the stack was created under the directory's name) are refused with the name to set, and no database password is generated while any volume of the stack exists, because those passwords are read only when a volume is created.

**Which services read which env file.** Only the four services that read the settings store (`backend`, `jobs-worker`, `auth`, `integrations-googleform`; they hold the master key, so they can read every stored value anyway) get `.env.deployment` as their `env_file`. The Temporal worker (it drives a browser on user-supplied URLs), the public webapp and the Typeform service each get an env file of their own (`.env.worker`, `.env.webapp`, `.env.typeform`, mode 600, git-ignored) holding only what that service reads, so a bug in the browser or the webapp cannot expose Stripe, Google or mail secrets, the Mongo credentials or any key. `deploy.sh` creates each file once from the lines of `.env.deployment` that service reads (empty values left out) and never changes it afterwards: edit those files for those services, not `.env.deployment`. Running `docker compose` without `deploy.sh`? The files are optional for rendering; create them yourself. The lists live in `deploy.sh` (`webapp_env_keys`, `worker_env_keys`, `typeform_env_keys`) and a test compares them with `docs/settings-inventory.md`. The Typeform service is a separate image whose source is not in this repository: its list is what its last released source read (plus the generated Mongo URI for a new stack).

**Services `deploy.sh` starts.** Every deployment starts the webapp, backend, auth, the Temporal worker, MongoDB and its seed, Temporal and its database, Umami and its database, nginx, **the admin service, the jobs worker (it consumes the `default` queue: `delete_user` and `delete_response`), the document sandbox and the task runner**, plus the Google and Typeform integrations when asked for (`./deploy.sh [both|googleform|typeform]`) and Polis with single sign-on. `./deploy.sh print-services [preference]` prints the list; a test runs it through `docker compose up --dry-run`. The first-sign-in notice and the setup token are shown only once the admin service reports healthy. If a first run stops after the keys were stored (a failed start, a closed terminal), the next run still shows the master key fingerprint and the notice (`BC_FIRST_RUN_PENDING` in `.env` marks it until shown).

**The Temporal worker and the actions executor** stay off the store. The worker runs a browser on user-supplied URLs, so it gets neither the master key nor a database role; it keeps `API_KEY` (the backend's `TEMPORAL_API_KEY`) and `AES_HEX_KEY` (the stack's `AUTH_AES_HEX_KEY`) in its environment. `settings-drift` compares both with the store. Rotating `AUTH_AES_HEX_KEY` or `TEMPORAL_API_KEY` therefore also means changing the worker's copy in `.env` until a separate worker key exists. The **Typeform** service is a separate image: it keeps `AUTH_JWT_SECRET`, `AUTH_AES_HEX_KEY` and `MASTER_ENCRYPTION_KEYSET` in its environment, so `settings-prune` keeps those three in the files while it is deployed.

**`deploy.sh` subcommands** (they need the stack's database running): `settings-import [--dry-run] [--prefer SERVICE]`, `settings-drift`, `settings-prune [--apply] [--swap] [--typeform | --no-typeform]`, `settings-env-export --keys A,B --out FILE`, `settings-set`, `settings-restore`, `settings-history`, `settings-verify`, `master-key-fingerprint` and `setup-token [--new]`: each runs the host command of the same name (table above) in a one-off container. `settings-import` reads `docker compose config --format json` on standard input, never from a file.

## Upgrading to 4.0

Back up first: the root `.env`, `.env.deployment` and the database.

1. `git pull` (or pull the release), then `./deploy.sh` as usual. It applies the migrations, then **imports** the settings your files carry into the store: the stack's keys (including the response keyset a stack that holds responses must keep), the Stripe, Google, Typeform, mail, analytics and other values that the services read. It never overwrites a stored value, stops on a value it refuses (a key that was published in the repository) or on services that disagree about a value (see `./deploy.sh settings-import --dry-run` and `--prefer SERVICE`), and prints only names and counts.
2. It then **compares** the store with the files (`settings-drift`) and stops if any value differs. Until you prune, an environment value wins over the store, so a stale value in `.env` or `.env.deployment` silently overrides a change made in the portal.
3. When the stack runs well, run `./deploy.sh settings-prune` to see what would be removed from `.env` and `.env.deployment`, and `./deploy.sh settings-prune --apply --swap` to do it (a private `.env.pre-v4.<time>` backup of each file stays; it holds the old secrets: delete it when you no longer need it). **Do this before rotating a key**: an environment value wins over the store, so a rotated key would be ignored by every service that still has the old one in its environment. Two root `.env` aliases are not setting names and are never pruned: `TRUSTED_PROXIES` and `STRIPE_REDIRECT_URL`; remove them yourself after the import.
4. **Changes to know about:**
   - `SETTINGS_MASTER_KEY` is now required by the backend, jobs worker, auth and the Google integration as well (they read the store; `SETTINGS_STORE=required`). Back it up; without it the store cannot be read.
   - `DEBUG` and `API_DOCS_ENABLED` are no longer pinned by the compose file. Both are off by default; set one in the portal or in `.env.deployment` deliberately.
   - `TRUSTED_PROXIES` is the `API_TRUSTED_PROXIES` setting now (the root `.env` value imports once).
   - Temporal's port 7234 is gone (compose network only). Umami's built-in login is replaced (above). The Temporal, Umami and Mongo databases keep their old passwords on an existing volume (table above); a new volume gets generated ones.
   - **Hardening of the deployment files.** (1) The webapp, the Temporal worker and the Typeform service no longer read `.env.deployment`: each reads its own file (`.env.webapp`, `.env.worker`, `.env.typeform`), which `deploy.sh` creates once from the lines of `.env.deployment` that service reads. Check them after the first deploy and move any other value those services need into them. (2) Umami's dashboard moved from `0.0.0.0:3003` to `127.0.0.1:3004`; port 3003 is now nginx and serves the tracker only, so `UMAMI_SCRIPT_URL` (`http://<host>:3003/script.js`) keeps working and the dashboard is reached through an SSH tunnel. (3) The admin service, jobs worker, document sandbox and task runner are started by `deploy.sh`. (4) `OAUTHLIB_INSECURE_TRANSPORT=1` is gone from the shipped `.env.deployment` (plain-http OAuth redirects now need it added deliberately); the inert `ADMIN_*` block is gone too (those settings belong in the root `.env`). (5) The Mongo `seeduser` account is removed. (6) `.env`, `.env.deployment` and every generated or exported env file are mode 600, and `.gitignore` covers every `.env.*` file except the examples. (7) A stack found under another compose project name is refused instead of being given new database passwords; the first-party images are pulled for every service, and the deploy stops when a schema migration fails.
   - Single sign-on (`SSO_*`) and the admin sign-in mail (`MAIL_*` in the root `.env`) stay environment-driven in this release, and are kept in the files by `settings-prune`.
   - `AUTH_CALLBACK_URI`, `UMAMI_URL` and the Typeform redirect values are no longer pinned by the compose file. `UMAMI_URL` is seeded with the compose-network address, `AUTH_CALLBACK_URI` has its code default (the auth address plus `/auth/callback`), and `TYPEFORM_REDIRECT_URI` / `TYPEFORM_SCOPE` now come from `.env.deployment`.
5. **Rollback.** Before pruning, set `SETTINGS_STORE=off` in the root `.env` and re-run `./deploy.sh`: the services read the files again. After pruning, put the `.env.pre-v4.*` backups back (or run `./deploy.sh settings-env-export --keys ... --out FILE` for just the values you need) and set `SETTINGS_STORE=off`. Rolling back the images to a release that predates the store does not need the store at all.

## Task runner: the responses data tasks

The `task-runner` service (backend image, no published port, own database role)
runs the tasks the portal will list. Two of them work on stored responses:

| Task | Does | Refuses with |
|---|---|---|
| `responses.check_undecryptable` | read-only: counts stored values that carry the ciphertext prefix but do not decrypt, per store and field (no ids, no values) | `store_not_configured`, `keyset_missing`, `keyset_unreadable`, `store_unreachable`, `store_empty` |
| `responses.backfill_workspaces` | stamps responses and deletion requests that predate `workspace_id`; a dry run first (required), resumable, idempotent; ambiguous records (a form linked to several workspaces with nothing to authenticate them) are never guessed and stay unstamped | the same codes |

Both need the data stores and the keyset in the runner's environment. The
compose service passes them from the root `.env`, and they are empty by default
(the tasks then refuse; nothing else changes):

| Variable | Meaning |
|---|---|
| `TASK_RUNNER_DATABASE_URL` | Postgres URL of the data role for the `app` schema. It defaults to `bc_tasks_data_app` (below), built from `BC_TASKS_DATA_APP_PASSWORD`; set it only to point at another dedicated role, never the backend's: that would give the runner the whole app schema next to the keyset |
| `TASK_RUNNER_GOOGLE_DATABASE_URL` | the same for the Google credentials (`google` schema); defaults to `bc_tasks_data_google` from `BC_TASKS_DATA_GOOGLE_PASSWORD`, never the integration's role |
| `TASK_RUNNER_MONGO_URI` / `TASK_RUNNER_MONGO_DB` | Mongo, while Mongo still holds responses (`TASK_RUNNER_MONGO_DB` defaults to `bettercollected_backend`). A read-only Mongo user is the recommended deployment for the check and for dry runs |
| `TASK_RUNNER_KEYSET` | the response keyset for the read-only `responses.*` tasks and `keyset.verify` when it is not in the settings store; it never goes to a file or a log. The `keyset.*` tasks that change or re-encrypt ignore it and use the settings store only |
| `DB_WRITE_MODE`, `DB_WRITE_MODE__RESPONSES`, `DB_WRITE_MODE__GOOGLE` | the services' write mode (from the root `.env`), so `keyset.*` re-encrypts the stores the services write and copies the primary's new ciphertext to the mirror |
| `TASK_RUNNER_GOOGLE_MONGO_DB` | the Google Forms integration's Mongo database (default `bettercollected_googleform`) |

`stores: auto` covers every configured store; `mongo`, `postgres` or `both` name
them and refuse if one is missing. The scripts `backend/scripts/check_undecryptable_values.py`
and `backend/scripts/backfill_response_workspaces.py` stay as command-line
tools (the backfill gained `--workspace-id` and `--form-id`), sharing the same code.

### The runner's data roles: `bc_tasks_data_app` and `bc_tasks_data_google`

`postgres/ensure-admin-roles.sh` (run by `deploy.sh` before the migrations and again after
them) creates two login roles, one per owning schema, with the passwords
`BC_TASKS_DATA_APP_PASSWORD` and `BC_TASKS_DATA_GOOGLE_PASSWORD` (generated once into the root
`.env`, URL-safe characters only, never printed). They are separate from `bc_tasks`, which holds
the runner's own state and the settings store. Why two: an UPDATE runs the table owner's triggers
and generated-column helpers with the updater's privileges. One role over `bc_app`'s and
`bc_google`'s tables would let either owner plant code that a re-encryption run executes with
access to the other's table. Each role holds no more than the owner of its schema already has, has
`search_path = pg_catalog`, and has USAGE on its own schema only. Column-level grants, nothing else:

| Role | Table | SELECT | UPDATE |
|---|---|---|---|
| `bc_tasks_data_app` | `app.form_responses` | `id`, `form_id`, `response_id`, `workspace_id`, `doc` | `doc`, `_bc_checksum` |
| | `app.responses_deletion_requests` | the same columns | `doc`, `_bc_checksum` |
| | `app.workspace_forms` | `id`, `form_id`, `workspace_id`, `doc` | none |
| `bc_tasks_data_google` | `google.oauth_credentials` | `id`, `user_id`, `doc` | `doc`, `_bc_checksum` |

No INSERT, DELETE, TRUNCATE or TEMPORARY; nothing in `admin`, `tasks`, `settings`, `auth` or `jobs`.
The grants are in the roles script, not in a migration, because the tables belong to other roles.
`tests/admin/tasks/test_data_role.py` pins the exact privilege set per role, that neither role can
reach the other's schema or anything its owner owns, and that a hostile trigger of either owner
gets nothing from the other.

Mongo, while it still holds responses: give the runner a dedicated user. For the check, `verify`
and dry runs a read-only user is enough (`read` on the responses database and the Google
integration's database). `responses.backfill_workspaces`, `keyset.reencrypt` and the other writing
tasks need `readWrite` on exactly `form_responses` and `Oauth2CredentialDocument` (the
credentials), and `read` on `workspace_forms`. Put its URI in `TASK_RUNNER_MONGO_URI`.

### Keyset tasks

`keyset.add_key`, `keyset.promote`, `keyset.reencrypt`, `keyset.verify` and `keyset.drop_old`
rotate `MASTER_ENCRYPTION_KEYSET`; the order and every guard are in
[response-keyset-rotation.md](response-keyset-rotation.md). They hold the locks `keyset` and
`responses.encryption`, so only one of them runs at a time.

## Task pages

`/tasks` lists the registered tasks (title, version, whether it changes data,
resumable, needs a prior dry run, locks) with the latest run of each. The portal
imports only the task catalog, the spec and the signing helpers, never an
implementation or the runner, so it cannot run a task itself: it writes a signed
row into `tasks.runs` and the runner executes it only if the signature verifies.

| Route | What it does |
|---|---|
| `GET /tasks/<name>` | the parameter form, generated from the task's `Params` schema (text with length limit and pattern, numbers with a range, enums as selects, flags as checkboxes, lists of ids one per line with a maximum count); a type the form cannot express is not rendered and says so, and a required one removes the start buttons. Shows the last dry run |
| `POST /tasks/<name>/dry-run` | CSRF, audited, at most 10 per admin per 5 minutes; no step-up. A read-only task has a single "Run" button that uses this route |
| `POST /tasks/prepare` | the code step: verifies a fresh authenticator or recovery code (same lockouts as `/api/stepup`) and renders a confirmation page that holds a single-use token. It changes no task state |
| `POST /tasks/<name>/apply` | needs that token, bound to hash(task, version, canonical params hash, `dry_run=false`) |
| `POST /tasks/runs/<id>/cancel` | token bound to the run id; sets `cancel_requested_at` (the only column the admin role may update); idempotent; only for queued or running runs |
| `POST /tasks/runs/<id>/resume` | token bound to the run id and its params hash; a new signed request with `resumes_run_id` and the same params |
| `GET /tasks/runs`, `GET /tasks/runs/<id>` | history (filters `task`, `state`, `page`) and one run: state, progress, the typed result (rendered through the task's `Result` schema; integers, booleans and ids only), the runner's refusal code with an explanation, sanitised events (code, counters, ids; 50 per page) and whether a checkpoint exists |
| `GET /api/tasks/runs/<id>?after=<seq>` | JSON for polling: state, progress and the events after `seq` |

Everything works without JavaScript (the run page has a Refresh link). The run
page loads one self-hosted script, `/static/tasks.js`, that polls the JSON every
two seconds while the run is active, shows a "Live" indicator and reloads once
when the run ends; it writes with `textContent` only. The content security
policy stays `script-src 'self'`.

### Look and fonts

The portal follows the interface's design system (`DESIGN.md`): paper-mist ground,
white panels on hairlines, one blue, Instrument Sans for text and JetBrains Mono
for values (setting keys, ids, hashes, task parameters). The tokens are CSS custom
properties on `:root` in `static/admin.css`, named like the webapp's; dark mode
follows `prefers-color-scheme` from the same roles. The latin woff2 files live in
`static/fonts/` (OFL-1.1, notices in `static/fonts/LICENSE`) and are served by
`/static/fonts/<name>.woff2` with `font/woff2`, `nosniff` and a one-year immutable
cache, the only response the portal lets a browser keep. Nothing is loaded from
another origin, so the content security policy is unchanged.

Starting a real run inserts the run row (state `queued`, signed as `tasks/request`)
and the `task.run.requested` audit row in one transaction; a task that requires a
prior dry run is refused unless a succeeded dry run of the same task, version and
params hash finished less than 24 hours ago and before now (the runner checks again
against the signed request time, and the page shows the runner's refusal code
if it still refuses). Parameters travel only in POST bodies, never in a URL, and
the audit row carries the validated parameters through the usual masking. All
refusals are fixed sentences that never repeat a submitted value.

## Background loops

In full portal mode (never in the bare gate) the service runs three loops. Each is
one asyncio task guarded by a Postgres session advisory lock on its own connection:
with several admin processes only one runs a given loop, the others stand by and
retry, and the lock is freed on shutdown (or when the connection dies). Intervals are
jittered, a failing pass is logged by exception class only (never a message, address
or payload), counted, and retried with a growing delay (up to 8 times the interval);
nothing a loop does can stop the service. `ADMIN_LOOPS_ENABLED=false` switches them
off (the old plain cleanup of sessions and counters then runs instead).

| Loop | Every | What it does |
| --- | --- | --- |
| `notifications` | 15 s | mails every address in `PLATFORM_ADMIN_EMAILS` about pending rows of `admin.notifications` |
| `retention` | 1 h | removes old rows, see the table below |
| `integrity` | 10 min | runs the settings store check and reads the keys services reported as rejected |

**Mail.** The text is fixed per kind (`settings.changed`, `settings.keyset_changed`,
`settings.keyset_reencrypt`, `tasks.run`, `settings.integrity`) and names only the
action, the setting or task, the version or run id and the requesting admin. Values,
parameters, payload fields a template does not print and key material are never
read. A row of an unknown kind, or a payload that does not fit its template, is
marked `failed` (`unknown_kind` / `bad_payload`) and never rendered. A row becomes
`sent` only when every current admin's mail was accepted; admins already served are
remembered as truncated digests, so a retry mails only the rest. A failing delivery
is retried after 1, 2, 4 and 8 minutes and then marked `failed` (`delivery_failed`).
At most `ADMIN_NOTIFY_MAX_PER_MINUTE` mails (30) go out a minute. Each batch writes
one audit row `notifications.batch` (actor kind `system`, counts only). If mail is
not configured (`MAIL_SMTP_SERVER`, `MAIL_SENDER`) the loop idles, rows wait, and the
status says `mail not configured`.

**Retention.** Every statement is bounded (1000 rows) so a backlog drains over several
passes. The audit log and the settings entries, history and manifest are never
touched.

| Data | Removed |
| --- | --- |
| sessions | ended more than 7 days ago |
| sign-in challenges | expired more than 1 day ago |
| rate-limit counters and used step-up tokens (`admin.attempts`) | older than 48 hours |
| `tasks.run_events` | older than 90 days |
| `tasks.checkpoints` | of runs finished more than 30 days ago |
| `settings.service_state` | rows older than 7 days of a service with no newer row (a service that still reports prunes its own) |

The admin role holds DELETE on `tasks.run_events`, `tasks.checkpoints` and
`settings.service_state` for this; the runner role still can only append.

**Integrity.** Any problem (a bad signature, a missing row, a manifest mismatch, a key a
service rejected) sets the integrity status and is mailed once per incident: the
same set of problems is not mailed again within 24 hours (kept in memory and, after a
restart, found through the outbox row's dedupe key). When the problems are gone the
status is ok again, and a later recurrence is a new incident.

**Seeing the status.** `Portal.loop_status()` returns each loop's last run, last
outcome (a short fixed phrase with counts), consecutive failures and whether this
process leads it; `Portal.integrity_status()` returns `ok` (None until the first
check), `(setting, reason)` pairs and the time of the check; `Portal.mail_status()` is
`ok` or `mail not configured`. All are in-memory copies of one shared holder
(`backend/admin/loops/status.py`) for the Health page and the shell banner.

| Variable | Default | Meaning |
| --- | --- | --- |
| `ADMIN_LOOPS_ENABLED` | `true` | run the loops |
| `ADMIN_NOTIFY_INTERVAL_SECONDS` | `15` | outbox pass interval |
| `ADMIN_NOTIFY_MAX_PER_MINUTE` | `30` | mail rate limit |
| `ADMIN_RETENTION_INTERVAL_SECONDS` | `3600` | retention interval |
| `ADMIN_INTEGRITY_INTERVAL_SECONDS` | `600` | integrity check interval |
